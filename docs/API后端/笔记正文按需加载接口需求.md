# 笔记正文按需加载：后端接口需求

> 状态：需求 1–4 已在 irisapi `Timmi` 分支实现（2026-09-26，未部署、未提交），接口细节见 irisapi `docs/notes-api.md`；客户端已实现元数据同步与混合模式（2026-09-27：镜像只存元数据，按正文哈希下载变化的正文；置顶、星标、有草稿、未同步和最近打开的 300 篇保留正文，其余只留摘要，打开时经需求 1 下载；旧服务端保持完整模式、不淘汰），尚未与部署后的后端联调
> 提出日期：2026-09-25
> 客户端对应：缓存重构第二期「混合模式」

## 1. 背景与目标

客户端是本地优先的：每篇已同步的笔记在本机保存完整正文，另外 `note_sync_mirror` 里还保存一份云端返回的完整 JSON（含正文），占用约为正文的 2 倍，并且随笔记数量线性增长。

第二期要改成**混合模式**：

- 置顶、星标、有草稿、未同步、最近访问的笔记：本地保留完整正文（离线可读）。
- 其余已同步笔记超出本地容量上限后：本地只保留元数据和摘要，打开时再下载正文。
- 同步链路只比对元数据和正文摘要，不再为了比对而保存第二份正文。

要做到这些，客户端需要两样后端目前没有的能力：**按 ID 取单篇笔记**，以及**只返回元数据的同步**。

## 2. 现状：客户端目前依赖的接口

| 接口 | 用途 | 问题 |
|---|---|---|
| `GET /api/notes/snapshot?limit=&cursor=&snapshot_token=` | 分页拉取全量快照 | 每条都带完整 `content` |
| `GET /api/notes/changes?cursor=&limit=` | 增量变更 | `upsert` 事件带完整 `content` |
| `GET /api/notes` | 旧版全量列表 | 只能整表拉取，无法取单篇 |

客户端解析的笔记结构（`CloudNote`，见 `src/features/notes/api/notes-sync.types.ts`）：

```ts
{
  id: number;              // 服务端 ID
  user_id: number;
  client_id: string;       // 客户端生成的稳定 ID
  version: number;         // 每次修改递增，客户端据此判断新旧
  title: string;
  content: string | null;
  category_id: number | null;
  created_at: string;
  updated_at: string | null;
  sync_updated_at: string | null;
  deleted_at: null;
  is_pinned: boolean | null;
  is_starred: boolean | null;
}
```

## 3. 需求

### 需求 1（必需）：按 ID 获取单篇笔记

```
GET /api/notes/:id
Authorization: Bearer <token>
```

**成功 200**：返回单个 `CloudNote`，字段与快照中的一条完全一致（含完整 `content` 与当前 `version`）。

**错误**：

| 状态码 | 含义 | 客户端处理 |
|---|---|---|
| 401 | 登录失效 | 走现有的登录失效流程 |
| 404 | 属于其他用户 | 与“不存在”相同，不返回 403，不泄露是否存在 |
| 404 | 不存在 | 从本地移除元数据 |
| 410 | 已删除（在回收站或已彻底删除） | 按删除事件处理；响应体 `data` 为 `{id, client_id, version, deleted_at}`，与同步里的删除事件一致（已彻底删除时为清理发出的删除事件版本） |

错误响应体沿用同步接口现有格式 `{ "error": { "code": "...", "message": "..." } }`，404 的 `code` 为 `NOTE_NOT_FOUND`、410 为 `NOTE_DELETED`。客户端据此把“笔记不存在”与“接口尚未上线（路由不存在）”区分开（见第 4 节）。

要求：

- 只能取到当前登录用户自己的笔记。
- 响应与 `snapshot`/`changes` 中同版本的数据逐字段一致（客户端会拿 `version` 与本地比对）。
- 与其他读接口相同的云存储授权规则。

### 需求 2（必需）：同步接口支持只返回元数据

`snapshot` 与 `changes` 增加可选参数 `fields=meta`：

```
GET /api/notes/snapshot?limit=50&fields=meta
GET /api/notes/changes?cursor=...&limit=50&fields=meta
```

传 `fields=meta` 时，每条笔记（包括 `changes` 的 `upsert.data`）：

- **不返回** `content`（字段省略，不要返回 `null`，以免和“正文为空”混淆）。
- **新增** `content_hash`：正文的 SHA-256，小写十六进制 64 位。计算对象是**数据库中存储的原始正文按 UTF-8 编码的字节**，不做任何规范化（不去空白、不转换换行）。正文为 `null` 时返回 `null`。
- **新增** `content_length`：正文的字符数（按 Unicode 码点计），正文为 `null` 时为 `0`。
- 其余字段与完整模式完全一致，`version`、分页、`snapshot_token`、`changes_cursor` 的语义不变。

不传 `fields` 时行为与现在**完全一致**，保证旧版客户端不受影响。

**参数白名单**：两个接口目前都对查询参数做白名单校验（`snapshot` 只允许 `cursor`、`snapshot_token`、`limit`，`changes` 只允许 `cursor`、`limit`，见 irisapi `src/router/notes-sync.ts`、`src/services/sync.ts` 中的 `allowKeys`），实现时需要把 `fields` 加入两处白名单。`fields` 只接受 `meta`，其他取值按现有规则返回 400 `INVALID_REQUEST`。

**分页一致性**（后端已定）：快照令牌与翻页游标绑定模式，`fields=meta` 建立的快照只能用 `fields=meta` 继续翻页，反之亦然，混用返回 400 `INVALID_CURSOR`；不带 `fields` 的快照标识与原来相同，旧令牌不受影响。`sync.changes_cursor` 与增量游标不绑定模式，两种模式可以交替使用。

### 需求 3（建议）：摘要字段

`fields=meta` 时额外返回 `content_preview`：正文前 120 个字符（按码点截断），截取后再把每个换行（CRLF、CR、LF）替换为一个空格；正文为 `null` 时为 `null`。

用途：在新设备上首次同步、本地还没有下载过正文时，笔记列表卡片也能显示摘要。如果不提供，客户端在这种情况下只显示标题。

### 需求 4（可选）：批量获取

```
GET /api/notes/batch?ids=1,2,3
```

最多 50 个 ID（重复的只取一次），返回 `{ data: CloudNote[], missing: number[] }`，`data` 按请求顺序排列；不存在、属于其他用户或已删除的 ID 都列入 `missing`，不区分原因。用于客户端在有网时预取置顶、星标笔记的正文。没有这个接口时，客户端会逐篇调用需求 1。

## 4. 兼容性与发布顺序

1. 后端先上线需求 1、2（参数可选，旧客户端不受影响）。
2. 客户端第二期版本发布，检测到接口可用后才启用按需加载；接口不可用时保持现在的全量本地模式。
3. **旧后端不会忽略 `fields` 参数**：现有的参数白名单会对未知参数返回 400 `INVALID_REQUEST`（“请求包含不支持的字段”）。因此客户端按以下规则判断“后端尚未支持”，并退回全量本地模式：
   - `GET /api/notes/:id` 返回 404 且响应体的 `error.code` 不是 `NOTE_NOT_FOUND`（即路由不存在）；
   - 带 `fields=meta` 的 `snapshot`/`changes` 返回 400 且错误码为 `INVALID_REQUEST`。

   客户端在一次启动内记住判断结果，不对每个请求反复试探；上述 400 不计入同步失败提示。

## 5. 验收用例（后端）

| # | 场景 | 期望 |
|---|---|---|
| 1 | 取自己的笔记 | 200，字段与快照一致 |
| 2 | 取别人的笔记 | 403 或 404，不泄露内容 |
| 3 | 取已移入回收站的笔记 | 410，带 `deleted_at`、`version` |
| 4 | `fields=meta` 快照 | 无 `content` 字段，`content_hash` 与完整正文的 SHA-256 一致 |
| 5 | 正文为空字符串 | `content_hash` 为空串的 SHA-256（`e3b0c442…`），`content_length` 为 0 |
| 6 | 正文为 `null` | `content_hash` 为 `null`，`content_length` 为 0 |
| 7 | 正文含表情、CRLF 换行 | 哈希按原始字节计算，不做换行转换 |
| 8 | 不传 `fields` | 响应与现在逐字节一致 |
| 9 | 修改正文后 `changes?fields=meta` | `upsert` 事件的 `version` 递增，`content_hash` 更新 |
| 10 | `fields` 取 `meta` 以外的值 | 400 `INVALID_REQUEST`，与现有参数校验一致 |
| 11 | 不存在的笔记 ID | 404，`error.code` 为 `NOTE_NOT_FOUND`，客户端可与“路由不存在”区分 |

## 6. 待确认问题（2026-09-26 后端答复）

1. 回收站里的笔记用 410 还是 404？**410 `NOTE_DELETED`**，已彻底删除的同样返回 410；只有从未存在或属于其他用户时返回 404。
2. `content_hash` 在写入时计算并存库，还是读取时计算？**读取时计算，不存库**，因此不需要数据库迁移。快照每页仍会从数据库读出全文再计算，元数据模式只减少返回给客户端的数据量。
3. 是否需要限制单篇正文的最大长度？**不新增限制**，沿用现有 5MB 请求体上限。
4. `fields=meta` 的快照令牌与游标能否和完整模式混用？**快照令牌和翻页游标不能混用，增量游标可以**（见需求 2“分页一致性”）。
