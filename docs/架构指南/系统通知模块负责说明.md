# 系统通知模块负责说明

> 适用范围：IRisNote Android/iOS 客户端的**系统通知**（待办提醒、常驻运行状态、测试通知、Android 16 动态通知）与**精确闹钟权限**链路。
> 本文描述的是**当前工作区代码现状**。Android 16 动态通知包含 ProgressStyle、Live Updates 提升请求、原生后台时间线及可选前台服务；真机展示仍待验收。
> 与既有文档的分工：`docs/UI/通知渠道适配.md` 记录渠道**决策过程**（为何用/不用某渠道），本文记录**模块职责与运行链路**；`docs/架构指南/项目架构与文件索引.md` 是全仓索引，本文是其通知部分的展开。

## 一、模块总览（分层职责）

```
┌────────────────────────── UI 层（features/settings）──────────────────────────┐
│ PermissionSettingsScreen（权限页：通知/准时提醒/常驻通知/相机/照片/安装更新）      │
│ HelpFeedbackScreen（帮助页：导出诊断日志、发送测试通知）                          │
└──────────────┬──────────────────────────────────┬─────────────────────────────┘
               │ useSystemNotifications()          │ 动态 import service
               ▼                                   ▼
┌────────────── Context / Provider 层（core/system-notifications）──────────────┐
│ system-notification-provider.tsx   三态装配：Expo Go 降级 / lazy 加载 / native  │
│ system-notification-native-provider.tsx  生命周期：前台分流、refresh、点击路由    │
│ system-notification-context.ts     Context 契约                                 │
└──────────────┬────────────────────────────────────────────────────────────────┘
               ▼
┌────────────── Service 层（system-notification.service.ts，唯一发送出口）────────┐
│ 渠道创建 ×3｜权限（应用级 + 渠道级）｜排程/取消｜常驻通知｜测试通知｜精确闹钟读取   │
└──────┬───────────────────────────────┬────────────────────────────────────────┘
       ▼                               ▼
┌─ 本地原生模块 ─────────────┐   ┌─ expo-notifications（SDK 57）─────────────────┐
│ modules/irisnote-system    │   │ scheduleNotificationAsync / Channel / Handler  │
│  getExactAlarmAccess()     │   │ 底层：Android NotificationManager + AlarmManager│
│  saveDiagnosticLog()       │   └────────────────────────────────────────────────┘
└────────────────────────────┘
       │
┌──────▼─────────────── 业务消费方（features/todos）──────────────────────────────┐
│ todo-reminder.service.ts    保存后资格判断 + 权限/精确闹钟横幅                     │
│ todo-reminder-coordinator.ts 对账引擎（孤儿取消/绑定保留/强制重排/先落库再排程）    │
└────────────────────────────────────────────────────────────────────────────────┘
       │
┌──────▼─────────────── 支撑设施 ────────────────────────────────────────────────┐
│ core/diagnostics            诊断日志（JSONL，所有链路的埋点出口）                  │
│ system_preferences 表（迁移 0011）  常驻通知开关 + 精确闹钟状态持久化              │
└────────────────────────────────────────────────────────────────────────────────┘
```

**核心原则**：所有"发通知"的动作单点收口在 `system-notification.service.ts`；provider 只管生命周期与分流；todos 模块只产生"待办提醒"这一类业务通知；诊断日志横切所有层但绝不记录待办正文与账号标识。

| `ensureRuntimeNotification()` | 幂等展示常驻通知：渠道初始化 → presented 里已有 `RUNTIME_NOTIFICATION_ID` 则跳过 → 否则立即展示（sticky） |

## 三、通知分级

### 3.1 五条业务链路 × Android 渠道对照

| 维度 | 待办提醒 | 常驻运行状态 | 测试通知 | 动态通知测试 | 待办进行中（动态） |
|---|---|---|---|---|---|
| 渠道 ID | `irisnote.reminders.v1` | `irisnote.runtime.v1` | `irisnote.diagnostics.v1` | `irisnote.live-todo.v1` | `irisnote.live-todo.v1` |
| 渠道名（用户可见） | 待办提醒 | 运行状态 | 通知测试 | 待办进行中 | 待办进行中 |
| importance | **HIGH（4）** | **LOW（2）** | **DEFAULT（3）** | **LOW（2）** | **LOW（2）** |
| 声音 | default | **无**（null） | default | **无** | **无** |
| 震动 | 是 | **否** | 是 | **否** | **否** |
| 锁屏可见性 | PRIVATE | PRIVATE | PRIVATE | PRIVATE | PRIVATE |
| 角标 | 否 | 否 | 否 | 否 | 否 |
| 通知内容 | 标题"待办提醒"，正文为待办摘要（≤100 字，已去控制字符） | 固定标题"IRisNote正在运行" | 固定测试文案 | 标题"模拟待办：60 秒专注任务"，正文为分钟进度 | 标题=待办摘要（脱敏），正文=分钟进度或"已开始 HH:MM" |
| 展示方式 | 到点触发 | `sticky:true + autoDismiss:false`（不可侧滑、常驻通知栏） | `autoDismiss:true`（可滑动清除） | 与真实待办同一 ProgressStyle/提升式/后台时间线；60 秒结束撤卡 | ProgressStyle 进度卡片：前台分钟级，退后台交原生闹钟续算；真实卡上限 3 条 |

| 点击行为 | 校验当前账号 → 选中对应日期 → 跳 `/(tabs)/todo`；失效则横幅提示 | 仅记日志，无跳转 | 仅记日志，无跳转 | 启动应用主界面（无深链） | 启动应用主界面（无深链） |

### 3.2 Android importance 档位语义（AOSP 标准）

| 档位 | 行为 | 本模块用途 |
|---|---|---|
| HIGH（4） | 有声 + 横幅弹出（heads-up） | 待办提醒——用户明确设定的到点事项 |
| DEFAULT（3） | 有声、状态栏图标，无横幅（部分 ROM 会升级展示） | 普通测试通知 |
| LOW（2） | 无声、仅状态栏与通知列表 | 常驻通知、待办进行中动态卡片——持续存在但不打扰 |
| NONE（0） | 完全关闭 | 用户在系统设置中把"待办提醒"渠道改为关闭时，`permission()` 复合判断整体视为未授权，App 内不再排程 |

注意事项：① 渠道 importance 创建后**代码不可变更**，用户只能在系统设置调整；② 渠道级关闭（NONE）不会被应用级权限查询发现，因此 `permission()` 单独做了渠道检查；③ 国产 ROM 可能重排/聚合通知，实际表现以真机为准（本模块全部走标准 Channel API）。

## 四、从 UI 到实际通知的全链路

### 4.1 链路 A：待办提醒（用户保存待办 → 到点提醒）

```
用户在待办表单点"确认保存"（TodoFormDialog）
  └─ store 提交事务（提醒字段随待办一起落库，绝不因通知失败回滚）
      └─ useSystemNotifications().afterSave(todo, "confirm")
          └─ afterSavedTodoReminder（todo-reminder.service）
              ├─ 会话过期检查（owner/generation 变了就放弃）→ after_save_stale
              ├─ 资格判断 desiredTodoReminder：未启用提醒/已完成/无开始时间/时刻已过 → after_save_ineligible
              ├─ 通知权限：permission() 复合查询；未授权且可再问 → requestSystemNotificationPermission（弹窗）
              │    仍拒绝 → showDisabled 横幅（"待办已保存，系统提醒尚未开启" + 开启按钮）
              ├─ 【新增】通知已授权时读 exactAlarmAccess()：
              │    denied → showExactAlarmDisabled 横幅（"系统可能延迟到点提醒" + 去开启按钮）
              └─ coordinator.reconcile() 触发对账 ↓

对账引擎 run()（coordinator，单例串行、循环消化 dirty）
  ├─ 快照：系统已排程集合 scheduled + 数据库绑定列表 bindings → reconcile_snapshot
  ├─ 孤儿清理：排程前缀 irisnote.todo. 匹配但数据库无绑定/账号不符 → cancel → orphan_cancelled
  ├─ 保留判断：绑定仍有效 + 待办未变 + 系统仍有该排程（且本轮非 forceReschedule）→ binding_retained，跳过
  ├─ 需要变化 → cancel 旧绑定（失败 → 绑定置 cancel 态等待重试，阻止新排程 → binding_cancel_failed）
  └─ 需要排程：
      ├─ 权限不足 → 绑定置 error"系统提醒尚未开启" → schedule_blocked
      ├─ 先写库：bindings.put(state=scheduling, notification_id=todoNotificationIdentifier(...))
      ├─ systemNotifications.schedule(id, at, summary, data)
      │    └─ expo-notifications DATE trigger + reminders.v1
      │        └─ Android：有精确闹钟权限 → AlarmManager.setExactAndAllowWhileIdle（准时）
      │                  无权限     → 非精确窗口（Doze 下可能延迟数分钟）
      └─ 成功 → 绑定置 scheduled → binding_scheduled；期间待办又变了 → 立刻 cancel 重进循环

到点（系统触发，App 可能被杀）
  └─ Android 系统按渠道展示通知（HIGH：声音+横幅）
      ├─ App 在前台：setNotificationHandler.handleNotification
      │    ├─ data.kind 为 runtime-status / diagnostic-test → 走各自分支（见 4.2/4.3）
      │    └─ 待办载荷：解析 + resolveReminderTarget 按当前账号找目标
      │         找到且仍启用未完成 → 显示；否则静默丢弃 → delivery_evaluated
      └─ 用户点击通知 → addNotificationResponseReceivedListener
          └─ effect：去重（identifier:date:action）→ 记 response_received
              ├─ 非待办载荷 → clearLastNotificationResponseAsync 后结束
              └─ 待办载荷：账号匹配 → selectTodoDate 选中日期 → router.push /(tabs)/todo
                  目标不存在 → 横幅"该提醒对应的待办已删除或不属于当前账号"
                  最后 clearLastNotificationResponseAsync（防冷启动重复消费）
```

### 4.2 链路 B：常驻通知开关（权限设置页）

```
权限页 Switch 点击（仅 Android 且非 Expo Go）
  └─ setRuntimeNotificationEnabled(value)（native-provider）
      ├─ 开启：requestApplicationNotificationPermission
      │    ├─ 拒绝 → 横幅"请先开启系统通知"，偏好不落库，开关保持关
      │    └─ 授权 → preferences.setRuntimeNotificationEnabled(true) 落库
      │              → ensureRuntimeNotification：渠道初始化（幂等）
      │                 → 已在通知栏（按 RUNTIME_NOTIFICATION_ID 查 presented）→ 跳过
      │                 → 否则立即展示 sticky 通知 → presented
      └─ 关闭：落库 false → removeRuntimeNotification（cancel+dismiss）→ removed
  失败 → toggle_failed(error) + 横幅"常驻通知开启/关闭失败"

冷启动 / 回前台 refresh()：
  runtimeEnabled = 偏好读取 && 应用权限 granted → ensureRuntimeNotification（幂等补偿）
  → 用户手动清了通知栏也会在下次回前台时按偏好恢复
```

### 4.3 链路 C：测试通知（帮助与反馈页）

```
"发送测试通知"点击（Web/不支持平台禁用；testing 防重入）
  └─ 动态 import service（避免安全入口静态加载 expo-notifications）
      ├─ requestApplicationNotificationPermission：拒绝 → 横幅"请先在系统设置中开启通知"
      └─ sendDiagnosticTestNotification：diagnostics.v1 渠道 → 立即展示可关闭通知
          → 横幅"测试通知已发送，本次操作已写入诊断日志"
  前台收到：handler diagnostic-test 分支正常弹横幅+声音；点击仅记日志
```

### 4.3.1 Android 16 模拟待办动态通知

帮助与反馈页点击「测试待办动态通知」后先请求应用通知权限，再调用 Provider 的 `startTodoLiveDemo(onTick)`。Provider 创建一条从当前时刻到 60 秒后的临时时间线，固定通知 ID 7001，注入 `TodoLiveUpdateCoordinator`。协调器用真实待办同一 `postLiveUpdate` 端口发 ProgressStyle 卡；`hasPosted(7001)` 确认发送成功后才开始计时。模拟记录仅在内存中，不写 SQLite、待办仓库或同步队列，也不占三张真实卡片额度。

按 Home 退后台时，Provider 调用 `handoff()`，真实卡与模拟卡一同交给 `scheduleLiveTodoCards`，原生持久化快照并用 AlarmManager 续算；开启「后台实时刷新」时，前台启动的服务也读取同一时间线做秒级更新。60 秒后原生接收器按结束时刻撤卡；JS 仍运行或下次回前台时也会清理。离开帮助页会主动取消。闹钟采用非精确 `setAndAllowWhileIdle`，省电模式下后台自动撤卡可能延迟，真机验收须观察。

### 4.4 链路 D：冷启动 / 回前台对账（refresh，精确闹钟的枢纽）

```
native-provider mount（数据库就绪后，迁移 0011 必已完成）/ AppState → active
  └─ refresh()：
      ① initializeSystemNotifications()（HIGH 渠道）
      ② permission 复合查询 → setPermission
      ③ 精确闹钟对账：
          current  = exactAlarmAccess()（实时读 AlarmManager）
          previous = preferences.exactAlarmAccess()（上次落库值）
          forceReschedule = current==="granted" && previous!=="granted"
          coordinator.reconcile({ forceReschedule })   ← 授权后强制重排
          current!=="unavailable" → preferences.setExactAlarmAccess(current) 落库
          previous==="denied" && forceReschedule → 横幅"准时提醒权限已开启，已有未来提醒已重新安排"
      ④ 常驻通知恢复（见 4.2）
      失败 → provider_refresh_failed(error) + 横幅"系统提醒暂不可用"
      finally → runtimeNotificationPending=false
```

provider mount 首次还会执行 `clearStaleLiveUpdates()`（进程内一次）：按 live-todo 渠道整清 + 无条件撤演示 ID 7001——进程被杀时 JS 无机会撤卡，ongoing 卡片用户不可滑除，靠下次启动清理兜底（原生 `cancelProgressNotificationsByChannel`，失败仅记 `stale_clear_failed` 诊断）。

## 五、精确闹钟权限（本次新增）

### 5.1 背景：为什么需要

- Android 12（API 31）引入 `SCHEDULE_EXACT_ALARM`：应用需持权才能用 `AlarmManager.setExact*` 精确触发；用户可随时在系统设置撤销。
- Android 14（API 34）起**新装应用默认拒绝**该权限，必须引导用户手动开启。
- `expo-notifications` 的 DATE trigger 在有权限时用 `setExactAndAllowWhileIdle`（Doze 下仍准时）；无权限自动退化为非精确调度，**Doze/省电下提醒可能延迟数分钟**。
- 项目早期决策（见 `docs/UI/通知渠道适配.md`）是"首版不声明精确闹钟，接受延迟"；本次变更为：声明权限 + 引导授权 + 授权后自动重排，把"准时"变成用户可选能力。

### 5.2 权限声明（单一来源：模块 manifest，gradle 合并进最终 APK）

| 位置 | 内容 |
|---|---|
| `modules/irisnote-system/android/src/main/AndroidManifest.xml` | `SCHEDULE_EXACT_ALARM`；`POST_PROMOTED_NOTIFICATIONS`（API 36.1 提升式安装级权限，低版本系统自动忽略）；`WRITE_EXTERNAL_STORAGE`（`maxSdkVersion=28`，仅旧版保存日志） |
| `app.json` → `android.permissions` | **不声明上述权限**（单一来源约束：`tests/todos/system-notifications.test.cjs:304` 断言 Expo 最终配置 manifest 不含 `SCHEDULE_EXACT_ALARM`，防止 app.json 重复声明漂移） |

同 manifest 还声明了 `WRITE_EXTERNAL_STORAGE`（`maxSdkVersion=28`），仅用于 Android 9- 保存诊断日志到公共下载目录，Android 10+ 走 MediaStore 无需此权限。

### 5.3 读取链路与四态语义

```
exactAlarmAccess()（service）
  ├─ 非 Android（iOS/Web）        → "not-required"
  ├─ NativeSystem 为 null（Expo Go / 模块未链接）→ "unavailable"（access_unavailable 警告日志）
  ├─ 读取异常                     → "unavailable"（access_read_failed 错误日志）
  └─ Kotlin getExactAlarmAccess：
       SDK < 31                   → "not-required"（系统天然允许精确）
       canScheduleExactAlarms()==true  → "granted"
       canScheduleExactAlarms()==false → "denied"
```

| 状态 | 含义 | UI 表现 |
|---|---|---|
| `not-required` | 系统 < Android 12，无需授权 | 权限页显示"无需授权"（行禁用） |
| `granted` | 已授权，提醒将准时触发 | 权限页"已允许" |
| `denied` | 未授权，提醒可能延迟 | 权限页"未允许"（可点击跳系统设置）；保存待办后横幅提示 |
| `unavailable` | 运行环境读不到（Expo Go） | 权限页"正式安装包中可用"（行禁用） |

### 5.4 授权后自动重排（forceReschedule 机制）

问题：expo-notifications 在**排程时刻**决定精确/非精确。已存在的排程不会因后来授权而升级，必须取消重建。

```
refresh() 检测 current="granted" 且 previous≠"granted"
  → coordinator.reconcile({ forceReschedule: true })
      → run(forceReschedule)：保留短路的条件 !forceReschedule && … 失效
      → 所有仍有效的未来提醒绑定走完整"取消 → 重新落库 → 重新 schedule"流程
      → expo-notifications 在已授权状态下重新以 setExactAndAllowWhileIdle 调度
  → 成功后横幅告知"已有未来提醒已重新安排"（仅 previous==="denied" 时展示，避免每次冷启动重复打扰）
  → current 落库，下一轮 previous==="granted"，forceReschedule 自然为 false
```

状态持久化：`system_preferences.exact_alarm_access ∈ {not-required, granted, denied}`（`unavailable` 不落库，避免 Expo Go 污染真实状态）。

### 5.5 用户触点

| 场景 | 入口 | 行为 |
|---|---|---|
| 主动查看/开启 | 权限设置页"准时提醒"行（AlarmClock 图标） | 只读状态 + 点击跳 `ACTION_REQUEST_SCHEDULE_EXACT_ALARM`；返回 App 后自动刷新（focus + AppState 监听） |
| 被动提醒 | 保存带未来提醒的待办（确认保存且通知权限已授予）时检测到 `denied` | 横幅"待办已保存，准时提醒权限尚未开启 / 系统可能延迟到点提醒"+「去开启」按钮 |
| 授权回流 | 从系统设置返回 App | `AppState → active` 触发 refresh → 检测状态变化 → 强制重排 + 成功横幅 |

### 5.6 平台差异

| 环境 | 行为 |
|---|---|
| Android 12+（API 31+） | 完整链路：四态读取、设置跳转、强制重排 |
| Android 11 及以下 | `not-required`，系统允许精确，无 UI 入口 |
| iOS | `not-required`（UNUserNotificationCenter 系统调度，无此概念） |
| Expo Go | `unavailable`（本地模块未链接），权限页显示"正式安装包中可用" |
| Web | 整个通知模块短路（`supportsSystemNotifications=false`） |

## 六、示范案例（端到端推演）

### 案例 1：保存一个"明天 9:00 提醒"的待办（权限全齐）

```
用户 22:00 保存待办（开始时间 明天 09:00，提醒开关开）
① store 落库成功（提醒字段与待办同事务）
② afterSave("confirm")：资格通过（09:00 > 当前时刻）
③ permission() = granted（应用 + 渠道都开）
④ exactAlarmAccess() = granted → 无横幅
⑤ reconcile：生成 identifier = irisnote.todo.{ownerKey编码}.{todoId编码}
   先落库 binding(state=scheduling) → schedule → 系统返回同一 id → binding(state=scheduled)
⑥ 诊断日志序列：after_save_started → after_save_permission → after_save_exact_alarm
   → reconcile_requested → reconcile_snapshot → binding_scheduled → after_save_reconciled
⑦ 次日 09:00 AlarmManager 精确触发 → reminders.v1（HIGH）声音+横幅
⑧ 用户点击 → 账号匹配 → 选中该待办日期 → 跳转待办页 → response 清理
```

### 案例 2：同上，但精确闹钟未授权

```
④ exactAlarmAccess() = denied
   → 横幅"待办已保存，准时提醒权限尚未开启 / 系统可能延迟到点提醒"+ 去开启
   → 用户点「去开启」→ 跳系统精确闹钟页 → 开启 → 返回 App
⑧ AppState=active → refresh：current=granted, previous=denied → forceReschedule
   → 该绑定取消重建，重新以精确方式调度
   → 横幅"准时提醒权限已开启，已有未来提醒已重新安排"
   （若用户不授权：⑦ 的通知仍会发出，但可能延迟数分钟）
```

### 案例 3：到点时待办已被当前账号删除

```
⑦ 系统触发通知
   App 在前台：handleNotification → resolveReminderTarget 找不到目标 → show=false
   → 通知被 App 静默拦截（delivery_evaluated: targetFound=false）
   App 在后台：系统照常展示；用户点击 → effect 中 target=null
   → 不跳转，横幅"该提醒对应的待办已删除或不属于当前账号"
   （另一账号登录时收到旧账号提醒同样走此分支——ownerKey 隔离）
```

### 案例 4：开启常驻通知后杀掉 App

```
① 权限页打开 Switch：授权 → 落库 → 通知栏出现"IRisNote正在运行"（无声、不可侧滑）
② 用户从最近任务划掉 App（进程死）
③ 通知仍在通知栏（系统持有，与进程无关）
④ 重新打开 App → mount → refresh：偏好=true && 权限 granted → ensure → presented
   里已有该 id → already_presented，跳过（幂等）
   若期间用户系统"清除全部"通知 → ensure 重新展示，偏好仍生效
⑤ 用户关闭 Switch：落库 false → cancel+dismiss → 通知消失
```

### 案例 5：导出诊断日志（帮助页）

```
① 点击"导出诊断日志"（exporting 防重入）

④ Sharing.shareAsync(uri)（分享面板兜底）；分享不可用且未保存过 → 抛错 → "诊断日志导出失败"
```

## 七、诊断日志与隐私约束

- **存储**：`document/irisnote-diagnostics.jsonl`，JSONL，环形上限 400 条；Web/测试环境仅内存。
- **每条事件**：`{timestamp, level(info|warning|error), scope, event, details}`。
- **scope 一览**：`notifications`（权限/渠道/收发）、`todo_reminder`（保存/对账/排程/取消）、`runtime_notification`、`diagnostic_notification`、`diagnostics`（导出）、`exact_alarm`（权限读取/设置跳转/对账）、`application`（前后台）。
- **隐私红线**：只存计数、布尔、时间与 `opaqueDiagnosticId`（FNV-1a 8 位 hex）；**绝不存**待办正文、账号标识、令牌；文本统一脱敏（`bearer/token/authorization/password/cookie → [REDACTED]`）+ 截断 160 字符；导出 metadata 仅含版本/构建号/平台。
- 日志由各层 `void recordDiagnostic(...)` fire-and-forget，队列内部吞错，**诊断失败绝不影响业务**。

| 环境/条件 | 待办提醒 | 常驻通知 | 测试通知 | 动态通知（测试/进行中） | 精确闹钟 |

| 应用退后台/被杀 | 已排程提醒由系统兜底 | 常驻通知保留 | 不适用 | 退后台移交原生时间线，AlarmManager 按墙钟续算；可选前台服务秒级更新；进程被杀后接收器读持久快照，下次启动清理残留 | 不受影响 |

## 附：快速索引

- 发一条通知要改哪？→ 只需调 `system-notification.service.ts` 导出的对应函数；新通知类别需在 `types.ts` 加渠道常量 + `native-provider.tsx` 的 handler 加 `kind` 分流分支。
- 提醒不对账/丢失怎么查？→ 导出诊断日志，按 `todo_reminder` scope 的 `reconcile_* → binding_*` 序列定位。
- 提醒不准时？→ 查 `exact_alarm` scope：`access_read`/`state_reconciled` 的 status 与 forceReschedule 字段。
- 动态通知不显示？→ 先确认 Android 16（API ≥ 36）与正式安装包；再查 `live_update` scope（`demo_*` 模拟待办、`card_posted/updated/removed` 卡片、`coordinator_*` 启停）与系统设置中 live-todo 渠道是否被用户关闭。
- 动态通知不上岛？→ 提升式需 **API 36.1（QPR）+** 设备且系统设置未关闭本应用"实时更新"总开关；36.0 设备退化为普通进度卡片属预期。用户手动降级过提升通知后，政策禁止为同类内容重发提升式（详见通知渠道适配 §2.4 生命周期条款），真机验收时需观察该边界。
- 被杀后卡片残留？→ 下次启动 `clearStaleLiveUpdates` 自动清理；未清理时查 `live_update` scope 的 `stale_clear_failed`。
- 常驻通知行为异常？→ 查 `runtime_notification` scope 的 `state_reconciled/toggle_*/presented/removed`。
