# IRisNote 后续开发指南

本文档面向继续开发 IRisNote 的人员，说明修改现有功能或新增业务时应该改哪些文件、代码应放在哪里，以及如何保持当前架构边界。

文中的示例用于说明目录和调用方式，不代表对应功能已经存在。

## 全局状态反馈约定（已实现，真机待验收）

需要向用户显示非阻断的全局状态时，统一调用横幅通知入口，包括主动保存结果、主动同步进度与结果、持续服务器连接故障、草稿保存结果和根页面返回退出提示。不得在各页面自行新增同类 Toast、提示条或仅用于成功反馈的 Alert。

详细交互、场景、类型契约和代码示例见 [全局横幅通知设计与调用规范](../UI/全局横幅通知设计与调用规范.md)。统一入口为 `@/core/notifications` 的 `banner.show/update/resolve/dismiss`，已可导入。异步任务先调用 `captureNotificationSession()`，返回前检查会话仍有效；常驻故障由业务确认恢复后调用 `resolve`。

- 十分重要且未解决的故障固定常驻，普通通知在其下方并行显示，不能覆盖故障。
- 同一任务使用稳定 ID 更新；持续故障由状态协调层统一通知，恢复后调用 `resolve`，不要让每个 HTTP 请求分别弹错。
- 在真实业务结果确认后调用；必须区分本机已保存与云端已同步，不得提前显示成功。
- 自动保存恢复副本成功、后台同步无变化等保持静默；表单字段错误、删除／放弃编辑确认仍使用原有专用交互。
- 页面跳转不清除应用级通知；退出或切换账号清理会话通知，并防止旧异步回调带回过期信息。
- 新功能评审时明确“哪些状态需要显示、通知 ID、常驻或计时、可选动作、何时更新／关闭”，纳入接入验收。新增原生弹窗必须使用 `@/shared/ui/Overlay/app-modal` 的 `AppModal`，以接入全局通知插槽。

## 笔记阅读位置与进度组件（本地已实现，交互待验收）

- 查看器入口为 `src/features/notes/components/viewer/NoteViewer.tsx`；核心定位、会话及存储在 `src/features/notes/reading/`，生命周期适配在 `hooks/useReadingProgress.ts`。
- 本地先保存逻辑行、UTF-16 字符偏移、文本锚点与百分比，再等待未来云端接入。普通阅读每秒合并落盘，拖动结束、导航跳转、失焦及应用后台时尽力立即冲刷。不要恢复旧的“离开时写整数百分比”实现。
- 新增状态反馈：`reading-save:<ownerId>:<noteId>` 表示阅读位置读取或保存失败，调用 `@/core/notifications` 的 `banner.show`，`important`／`high`／`until-resolved`，带“重试”动作。失败未解决时保持显示；成功读取／落盘后 `banner.resolve` 并 `banner.dismiss`，正常自动保存静默。离开页面后的失败写入仍可通过横幅重试；跨异步工作使用 `captureNotificationSession()` 检查账户会话。
- 导航面板使用 `AppModal`，气泡在当前窗口内按坐标布局，不在拖动中打开原生 Modal。隐藏滚动条／气泡时卸载相应触摸节点。
- 标题及书签通过 `NoteViewer.navigationEntries` 显式接入；当前没有数据来源时展示“暂无段落标题或书签”，不得从普通正文推测标题。通用气泡入口为 `src/shared/ui/ProgressBubble/ProgressBubble.tsx`，接收窗口手指坐标、百分比 SharedValue、容器窗口坐标和交互回调。
- 后端暂缺：`reading-sync-contract.ts` 只有传输契约与守卫；`readingProgressStore.listPending(ownerId)` 可读取待同步快照。实际云端读写、恢复网络后补传和多端冲突联调未完成，不得显示已同步或把笔记正文同步成功等同于阅读位置同步成功。
- 字段、组件文件、接入示例和边界详见 [笔记查看进度组件](../UI/笔记查看进度组件.md) 第 11 节。设备交互验收由用户主动发起。

## 1. 先确定代码属于哪一层

开发前先回答三个问题：

1. 它是否定义 URL、Layout 或 Redirect？是则放 `src/app`。
2. 它是否只属于一个业务？是则放对应的 `src/features/<feature>`。
3. 它是否跨多个业务复用且没有业务语义？是则考虑 `src/shared`；如果属于应用壳层或主导航，则放 `src/core`。

错误示例：

- 把 Todo 请求写进 `src/app/(tabs)/todo/index.tsx`。
- 因为两个组件外观相似，就把带有“删除分类”逻辑的弹窗放入 `shared/ui`。
- 在 `shared/http/client.ts` 中加入笔记排序逻辑。

## 3. 新增普通页面

业务实现放在 Feature，`app` 只建立 URL。

假设为 Todo 新增详情页：

```text
src/features/todos/screens/TodoDetailScreen.tsx   真正页面
src/app/pages/todo/[id].tsx                       路由薄包装
```

路由文件：

```tsx
export { default } from "@/features/todos/screens/TodoDetailScreen";
```

Screen 示例：

```tsx
import { Screen } from "@/shared/ui";
import { useLocalSearchParams } from "expo-router";
import { Text } from "react-native";

export default function TodoDetailScreen() {
    const { id } = useLocalSearchParams<{ id?: string }>();

    return (
        <Screen variant="surface">
            <Text>Todo ID: {id}</Text>
        </Screen>
    );
}
```

如果页面需要在根 Stack 中配置动画或 Header，再将路由名加入 `src/app/_layout.tsx`。不需要特殊配置时，Expo Router 可自动发现页面。

## 4. 新增 Feature

只创建真实功能所需的目录。一个最小 Feature 可以只有 Screen 和入口：

```text
features/example/
├── screens/
│   └── ExampleScreen.tsx
└── index.ts
```

随着需求出现再增加：

```text
features/example/
├── api/                  # HTTP 请求
├── components/           # 只属于本业务的组件
├── hooks/                # 业务动作和状态组合
├── screens/              # 页面编排
├── services/             # 相机、剪贴板、文件等平台服务
├── example.types.ts      # 数据契约
├── example.cache.ts      # 确实需要运行时缓存时
├── example.events.ts     # 确实需要跨页面通知时
└── index.ts              # 稳定的公开出口
```

不要为了“目录看起来完整”提前创建空 API、Store、Hook 或类型文件。

## 5. 新增 API

### 5.1 先定义类型

```ts
// features/todos/todos.types.ts
export type Todo = {
    id: number;
    title: string;
    completed: boolean;
};

export type CreateTodoPayload = {
    title: string;
};
```

### 5.2 再写 API 文件

```ts
// features/todos/api/todos.api.ts
import api from "@/shared/http/client";
import type { CreateTodoPayload, Todo } from "../todos.types";

export async function getTodos(): Promise<Todo[]> {
    const { data } = await api.get<Todo[]>("/todos");
    return Array.isArray(data) ? data : [];
}

export async function createTodo(payload: CreateTodoPayload): Promise<Todo> {
    const { data } = await api.post<Todo>("/todos", payload);
    return data;
}
```

规则：

- 使用 `@/shared/http/client`，不要创建新的 Axios 实例。
- URL 使用相对路径，API 根地址由 Client 统一管理。
- 输入和响应必须有类型。
- 对数组、可空字段等不稳定响应在 API 层规范化。
- UI 层通过 `getApiErrorMessage` 获取错误文案。

## 6. Screen、组件和 Hook 如何分工

### Screen

负责：

- 请求时机。
- 页面级 loading/error/empty 状态。
- 路由参数和导航。
- 组合业务组件和 Hook。

不负责：

- 通用按钮底层样式。
- Axios Client 配置。
- 可复用的复杂手势细节。

### Components

业务组件优先通过 Props 接收数据和回调：

```tsx
type TodoItemProps = {
    title: string;
    completed: boolean;
    onToggle: () => void;
};
```

如果组件只服务于 Todo，放 `features/todos/components`；只有确认跨多个业务复用且无 Todo 语义时，才提升到 `shared/ui`。

### Hooks

Hook 适合封装一个完整业务动作，例如当前 `useNotePin`：

```text
读取旧状态
→ 乐观更新 UI
→ 调用 API
→ 成功保留
→ 失败回滚并提示
```

不要创建只包一行 API 调用、且没有状态或复用价值的 Hook。

## 7. 状态方案选择

| 场景 | 当前推荐方案 | 现有例子 |
| --- | --- | --- |
| 单个组件临时状态 | `useState` | 弹窗开关、表单输入 |
| 页面派生数据 | `useMemo` | 分类映射、筛选笔记 |
| 避免重复请求 | Promise Ref | NotesScreen、CategoryBar |
| 跨页面全局身份状态 | Context Provider | AuthProvider |
| 短生命周期详情缓存 | 模块级 Map | notes.cache.ts |
| 松耦合刷新通知 | 模块级事件订阅 | notes.events.ts、categories.events.ts |
| 需要重启后保留 | AsyncStorage | Token、User、Device ID |

项目虽然安装了 Zustand，但当前没有业务使用。只有在多个无父子关系页面需要频繁读写同一复杂状态、Context 或事件机制明显难以维护时，再评估引入 Store。

## 8. 事件和缓存示例

### 发布订阅

```ts
useEffect(() => {
    const unsubscribe = onNotesChanged(() => {
        void fetchNotes();
    });

    return unsubscribe;
}, [fetchNotes]);
```

订阅必须返回取消函数，组件卸载时必须解除监听。

### 缓存同步

当列表本地更新时，列表状态和详情缓存要同时更新：

```ts
setNotes((previous) => {
    const next = previous.filter((note) => note.id !== deletedId);
    setCachedNotes(next);
    return next;
});
```

当前编辑功能会更新单条缓存并广播笔记变更事件；后续调整保存流程时，必须同时检查列表刷新和详情缓存，不能只修改当前 Screen 的局部状态。
