## 1. 文档目的与使用规则

本文档用于指导 IRisNote 核心编辑器的后续设计、任务拆分、编码、迁移和验收。它不是对当前源码的描述，而是从当前纯文本编辑器逐步演进到块级、离线优先、支持版本历史和增量同步的目标实施规范。

后续涉及编辑器的代码变更必须先回答以下问题：

1. 变更属于本文档的哪个实施阶段？
2. 前置阶段是否已经完成并通过验收？
3. 是否改变了本文档中的业务不变量？
4. 是否需要迁移已有笔记数据？
5. 是否影响草稿恢复、历史版本、同步、容量或导出？
6. 是否已经更新本文档、`项目编辑器进度.md` 和 `CHANGELOG.md`？

### 1.1 规范关键词

- **必须**：后续实现不可绕过的业务或数据安全要求。
- **应该**：默认采用的方案；改变时必须记录理由和风险。
- **可以**：允许的扩展，不属于首版强制范围。
- **禁止**：会破坏数据一致性、历史边界或兼容性的做法。

### 1.2 决策状态

本文档使用三种状态标记：

| 状态 | 含义 | 后续处理 |
| --- | --- | --- |
| 已确认 | 已形成当前业务约束 | 修改前必须重新评审 |
| 暂定 | 可以用于设计，但应保持可配置 | 上线前需结合测试或成本复核 |
| 待决策 | 当前信息不足 | 不得在代码中暗自固定 |

## 2. 目标与非目标

### 2.1 总体目标

IRisNote 编辑器最终应具备以下能力：

- 笔记按稳定 ID 的内容块组织。
- 文字、Markdown、代码、图片、附件、思维导图和画布使用明确的块类型。
- 编辑过程首先修改本地草稿，不直接覆盖当前稳定版本。
- 应用异常退出后可以恢复未保存草稿。
- 撤销和重做只作用于当前未保存版本。
- 只有用户点击保存才创建正式历史版本。
- 保存时执行基础版本校验，避免多设备静默覆盖。
- 每个块、附件和版本拥有可验证的内容哈希。
- 手动同步与自动同步共用同一增量同步引擎。
- 图片、附件和未变化块不重复上传。
- 支持笔记逻辑大小、账户实际占用和云空间配额。
- 画布块支持背景、图片和手写等图层。
- 旧的字符串正文可以安全迁移，并能在失败时回滚。

### 2.2 首版非目标

以下能力不属于第一阶段目标：

- 多人实时协作。
- CRDT 或 OT 实时合并。
- 自动进行复杂的跨设备块级冲突合并。
- 无限画布。
- 手写笔迹覆盖会自动重排的流式文字。
- 跨用户附件去重。
- 在第一版同时完成端到端加密、云草稿和后台实时同步。

这些能力必须在基础草稿、版本和迁移链路稳定后再评估。

## 3. 当前实现基线与差距

截至本文档制定时，IRisNote 的笔记模型和编辑流程主要具备以下特征：

| 当前文件 | 当前职责 | 与目标架构的差距 |
| --- | --- | --- |
| `src/features/notes/notes.types.ts` | 使用 `content: string | null` 表示正文 | 没有块、版本、草稿和哈希模型 |
| `src/core/editor/` | 提供跨业务纯文本输入状态、通用编辑界面和公共出口 | 只有纯文本外壳，没有块、选择区、命令和撤销能力 |
| `src/features/notes/components/editor/NoteEditor.tsx` | 将 Note 适配给通用编辑器，并负责校验、API、缓存和事件 | 没有持久化草稿、撤销边界和保存事务 |
| `src/features/notes/screens/EditNoteScreen.tsx` | 按 ID 优先读取进程内缓存，缺失时请求列表 | 没有编辑会话和基础版本选择 |
| `src/features/notes/notes.cache.ts` | 使用模块级 `Map` 缓存笔记 | 应用重启后消失，不能承担草稿恢复 |
| `src/features/notes/api/notes.api.ts` | 创建、更新和删除笔记 | 更新接口直接覆盖笔记，没有版本条件 |
| `src/features/notes/hooks/noteTextLength/` | 对完整字符串正文进行本地统计 | 块化后需要兼容拼接或增量统计 |
| `src/features/notes/components/NoteShare/` | 基于标题和字符串正文导出 | 块化后需要统一序列化与降级规则 |

因此，本计划是一次数据模型和业务边界升级，不是只替换 `TextInput` 或增加工具栏。

## 5. 核心术语与业务不变量

### 5.1 核心术语

| 术语 | 定义 |
| --- | --- |
| 笔记 Note | 稳定业务实体，保存标题、分类和当前版本指针等元数据 |
| 稳定版本 Revision | 用户点击保存后形成的不可变内容版本 |
| 基础版本 Base Revision | 本次编辑会话开始时所依据的稳定版本 |
| 编辑会话 Edit Session | 一次从基础版本开始的编辑生命周期 |
| 草稿 Draft | 尚未提交为稳定版本的本地持久化内容 |
| 内容块 Block | 具有稳定 ID、类型、顺序和负载的编辑单元 |
| 资源 Asset | 图片、文件等独立二进制对象 |
| 画布 Canvas | 支持固定坐标和图层的块类型 |
| 图层 Layer | 画布内部可排序、变换、显示和锁定的对象 |
| 根哈希 Root Hash | 由规范化版本清单计算出的内容身份 |
| 同步游标 Sync Cursor | 记录客户端已经处理到哪个服务端变更位置 |
| 墓碑 Tombstone | 用于跨设备传播删除行为的轻量记录 |

### 5.2 不可破坏的不变量

1. 稳定版本一旦创建，内容不可原地修改。
2. 草稿不得改变笔记的当前稳定版本指针。
3. 草稿写入不得创建用户可见历史版本。
4. 保存前必须先完成所有待写草稿任务。
5. 保存必须携带基础版本，并由服务端或本地版本仓库执行条件校验。
6. 保存失败或冲突时不得删除本地草稿。
7. 保存成功后，新版本成为下一次编辑的基础版本。
8. 撤销栈不得跨越保存边界。
9. 同一实体的异步写入必须串行，旧请求不得覆盖新状态。
10. 客户端提供的哈希不得被服务端无条件信任。
11. 删除必须通过墓碑或变更事件同步，不能只依赖“查询不到”。
12. 附件必须独立存储并通过引用使用，禁止在每个历史版本内重复复制。

## 6. 总体架构

```text
路由与 Screen
└── 业务编辑器适配层（Notes / Excerpts）
    ├── core/editor
    │   ├── 通用编辑器内存状态
    │   ├── 当前块树、选择区和焦点
    │   └── 当前版本撤销/重做操作
    └── 业务编辑会话协调器
        ├── 草稿服务
        │   ├── 脏块集合
        │   ├── 防抖和最长等待
        │   └── 串行持久化队列
        ├── 版本服务
        │   ├── 规范化版本清单
        │   ├── 哈希计算
        │   └── 保存事务与历史恢复
        ├── 本地数据库
        │   ├── 业务实体和版本
        │   ├── 块和草稿
        │   ├── 资源引用
        │   └── 同步队列和游标
        ├── 同步引擎
        │   ├── 手动/自动触发策略
        │   ├── 增量推送和拉取
        │   └── 冲突隔离
        └── 容量服务
            ├── 内容逻辑大小
            └── 账户实际计费占用
```

业务依赖方向应该保持为：

```text
app 路由 → Feature Screen/适配层 → core/editor
                                  → Feature 会话/领域服务 → 本地仓库/同步端口
```

`core/editor` 可以依赖 React、React Native 和 Shared，但禁止反向依赖 Notes、Excerpts 或其他 Feature。编辑器组件禁止直接拼接服务端请求、直接管理数据库迁移或直接修改当前版本指针。

## 7. 目标数据模型

以下结构是领域契约，不代表已经确定最终数据库字段名。

### 7.1 Note

一篇笔记应至少包含：

- `noteId`：稳定且全局唯一的笔记 ID。
- `ownerId`：所属用户。
- `title`：当前显示标题。
- `categoryId`：分类引用。
- `currentRevisionId`：当前稳定版本。
- `createdAt`、`updatedAt`。
- `deletedAt`：可空；删除后用于墓碑传播。
- 置顶、标星和排序等非正文属性。
- `schemaVersion`：笔记元数据结构版本。

### 7.2 NoteRevision

每次有效保存创建一个新版本：

- `revisionId`：历史节点 ID。
- `noteId`：所属笔记。
- `parentRevisionId`：直接基础版本。
- `rootHash`：版本清单根哈希。
- `manifest`：块顺序、块哈希和资源引用清单。
- `createdAt`。
- `createdByDeviceId`。
- `schemaVersion`。
- 可选保存说明或恢复来源。

即使两个版本内容相同，版本 ID 仍可能不同。哈希代表内容身份，版本 ID 代表历史身份。

### 7.3 EditSession

- `sessionId`。
- `noteId`。
- `baseRevisionId`。
- `draftId`。
- `startedAt`、`lastEditedAt`。
- `deviceId`。
- `status`：editing、saving、conflicted、closed。

### 7.4 Draft

- `draftId`。
- `noteId`。
- `baseRevisionId`。
- `titleDraft`。
- 草稿块或对基础版本的变化集合。
- `lastPersistedAt`。
- `dirty`。
- `schemaVersion`。

草稿可以采用完整草稿块表，也可以采用“基础版本 + 变化块”形式。第一版优先选择便于恢复和排错的实现，不应为了节省少量空间引入复杂重放链。

### 7.5 Block

所有持久内容块必须至少包含：

- `blockId`：稳定 ID，禁止使用数组下标作为身份。
- `type`：块类型。
- `orderKey`：顺序位置。
- `payload`：类型相关内容。
- `payloadHash`：规范化负载哈希。
- `schemaVersion`。
- `createdAt`、`updatedAt`。

同一块在版本之间内容未变化时，应复用内容身份，不重复存储等价负载。

### 7.6 Asset

- `assetId`。
- `ownerId`。
- `contentHash`。
- `byteSize`。
- `mimeType`。
- 本地 URI 和远端对象键。
- 上传状态。
- 引用计数或引用关系。
- 缩略图/预览引用。
- 创建时间和删除候选时间。

禁止将大型二进制 Base64 直接嵌入笔记块 JSON。

### 7.7 SyncQueueItem

- `queueItemId`。
- `entityType`：revision、block、asset、tombstone 等。
- `entityId`。
- `operation`：create、update、delete。
- `contentHash`。
- `attemptCount`。
- `nextRetryAt`。
- `status`。
- `lastError`。

同步任务必须可重试、可恢复并且具有幂等键。

## 8. 块模型规范

### 8.1 首批块类型

| 类型 | 负载 | 首版策略 |
| --- | --- | --- |
| paragraph | 文字及行内格式 | 必须 |
| heading | 层级和文字 | 必须 |
| markdown | Markdown 源码、解析版本和显示选项 | 作为独立源码块实现 |
| code | 语言、代码正文 | 必须 |
| image | 资源引用、说明和显示属性 | 附件阶段实现 |
| attachment | 资源引用、文件名和说明 | 附件阶段实现 |
| quote | 引用正文 | 可由基础文本能力扩展 |
| divider | 样式 | 可选 |
| checklist | 文本和完成状态 | 后续 |
| mindmap | 第三方或内部结构化负载 | 后期 |
| canvas | 画布尺寸、图层清单 | 画布阶段实现 |

### 8.2 Markdown 定位

结构化块是笔记的权威数据源。Markdown 的定位应为：

- 导入格式。
- 导出格式。
- 可选的 Markdown 源码块。
- 普通文本块的快捷输入语法。

禁止同时把“整篇 Markdown 字符串”和“整篇块 JSON”都当作权威数据，否则两者可能产生不一致。

### 8.3 块操作

编辑器至少需要定义以下领域操作：

- 插入块。
- 更新块负载。
- 删除块。
- 移动块。
- 拆分块。
- 合并相邻兼容块。
- 改变块类型。
- 批量粘贴和批量删除。

每个操作必须明确：

- 如何进入撤销栈。
- 如何标记脏块。
- 是否立即落盘。
- 是否影响附件引用。
- 如何生成哈希。

### 8.4 顺序与稳定身份

- 移动块不得改变 `blockId`。
- 删除块必须记录操作，而不是只从 UI 数组移除。
- 大规模移动时应避免为所有后续块重写连续整数位置。
- `orderKey` 的最终算法属于待决策项；实现前必须针对插入、移动和同步合并评审。

## 9. 编辑会话生命周期

### 9.1 进入查看页

```text
进入查看页
├── 读取本地稳定版本并快速展示
├── 检查本地是否存在未完成草稿
├── 普通草稿直接恢复到统一文本节点
├── 冲突草稿保留并显示紧凑确认
└── 单击定位光标；同区双击调起软键盘
```

既有笔记进入详情页时建立轻量草稿会话；未发生变化的序号仍为 0，不创建历史版本，也不触发云端保存。

### 9.2 激活输入

1. 读取当前稳定版本 `Vn`。
2. 检查是否存在基于 `Vn` 的可恢复草稿。
3. 如果草稿基础版本仍然有效，直接恢复草稿，不显示发现提示页。
4. 如果远端或本地当前版本已变化，保留草稿并标记冲突；用户明确确认后才重绑定当前基础版本。
5. 创建当前版本撤销栈。
6. 将编辑器内存状态初始化为草稿或稳定版本内容。

### 9.3 用户编辑

- 内存状态立即响应输入。
- 变化块加入脏块集合。
- 文本变化进入防抖保存流程。
- 结构变化立即排入本地保存队列。
- 撤销操作本身也必须重新标记对应脏块。

### 9.4 收起输入法保存本地草稿

```text
系统返回或顶部返回收起输入法
├── 完成输入法组合文本
├── 强制写完所有脏块
├── 保持当前草稿会话和编辑状态
└── 不创建 Revision、不更新稳定笔记、不访问云端
```

任一步失败时：

- 不得更新当前版本指针。
- 不得删除草稿。
- 必须恢复保存按钮状态并显示可理解的错误。
- 已经创建但未挂接的临时数据必须可以安全清理或复用。

### 9.5 离开合并页

- 有未保存修改时，必须先把草稿补写到本地。
- 在允许导航退出前读取完整草稿快照、校验 `baseRevision`，并在本地事务中提交稳定版本；无变化不创建版本。
- 本地提交成功后先允许页面退出，再由不依赖已卸载页面的同步协调器静默上传待同步版本。
- 同一篇笔记的退出上传必须串行；旧响应只能确认请求启动时的 Revision，不能把更新的本地版本误标为已同步。
- 云端接受后按草稿会话与序号条件清理；拒绝、结果未知或新会话已接管时保留草稿。
- 普通恢复草稿重新进入时直接展示，不再出现「发现本地草稿」整页提示。
- 冲突草稿未经明确确认不得覆盖稳定版本；保存失败继续保留草稿。

## 10. 草稿自动保存

### 10.1 保存策略

文本块的暂定策略：

- trailing debounce：停止输入 750ms 后保存。
- max wait：持续输入时最多 5 秒必须保存。
- 切换块：立即保存旧块。
- 输入框失去焦点：立即保存。
- 应用进入后台：立即请求保存全部脏块。
- 页面卸载或返回：立即保存全部脏块。
- 新增、删除、移动块：立即保存结构变化。
- 图片或附件导入完成：立即保存资源引用。

### 10.2 性能规则

- 只持久化变化块和必要的草稿元数据。
- 禁止每次按键序列化整篇笔记。
- 禁止每次按键请求服务器。
- 数据库写入使用异步接口。
- 同一个草稿使用单一串行队列。
- 队列中多个等价更新可以合并为最后状态。
- 不同语义操作不得错误合并，例如“新增附件”和“删除附件”。

### 10.3 竞态保护

保存队列必须保证：

1. 新负载不会被较晚完成的旧写入覆盖。
2. 写入进行中产生的新修改会在当前任务结束后继续处理。
3. 页面切换笔记后，旧笔记回调不能修改新笔记状态。
4. 每次保存任务携带 `draftId`、`sessionId` 和局部序号。
5. 数据库异常时脏状态保持为真，并允许重试。

### 10.4 生命周期限制

移动操作系统可能快速暂停或终止应用。因此“进入后台立即补写”是重要补偿，但不能成为唯一保障。正常输入期间必须持续写入本地；不能等到退后台时才第一次保存。

## 11. 撤销、重做与历史版本

### 11.1 当前版本撤销

- 撤销栈属于编辑会话，不属于永久历史。
- 连续文字输入按编辑器语义合并，而不是每个字符一个撤销项。
- 中文输入法组合期间不得产生错误的中间历史项。
- 粘贴、删除块、移动块、导入图片和一次完整手写笔画应形成独立撤销单元。
- 保存成功后必须建立新边界，禁止撤销回保存前状态。

### 11.2 永久历史

- 新建笔记首次保存形成 `V1`。
- 每次有实际变化的手动保存形成一个新版本。
- 没有内容或受版本管理元数据变化时，不创建空版本。
- 恢复旧版本不得修改旧节点，而应从旧内容创建新的当前版本。
- 历史版本保留策略可以按套餐配置，但清理行为必须可预测。

### 11.3 保存边界示例

```text
V10
└── 编辑草稿 A
    ├── 撤销/重做只在 A 内
    └── 点击保存 → V11
        └── 编辑草稿 B
            ├── 新的撤销/重做栈
            └── 点击保存 → V12
```

## 12. 规范化、哈希与内容身份

### 12.1 哈希层级

1. 每个块负载计算 SHA-256。
2. 每个附件文件计算内容哈希。
3. 版本清单包含块 ID、顺序、类型、块哈希和资源引用。
4. 对规范化版本清单计算整篇根哈希。

禁止使用数组内存顺序、对象键偶然顺序或本地文件 URI 直接计算跨设备哈希。

### 12.2 规范化规则

实现前必须固定以下规则：

- 字符编码统一为 UTF-8。
- JSON 键顺序稳定。
- 数字、布尔值和空值使用统一表示。
- 换行符统一。
- 明确是否保留尾随空格。
- 块顺序必须进入版本清单。
- 资源使用内容哈希或稳定资源 ID，不使用设备本地路径。
- 服务端生成时间、同步状态和本地缓存字段不得进入内容根哈希。
- 规范化算法本身具有版本号。

### 12.3 哈希职责

| 数据 | 职责 |
| --- | --- |
| `revisionId` | 表示历史身份 |
| `parentRevisionId` | 表示版本因果关系 |
| `rootHash` | 表示版本内容身份 |
| `blockHash` | 定位变化块和复用内容 |
| `assetHash` | 校验和去重附件 |
| `syncCursor` | 表示客户端同步进度 |

哈希不能替代版本号、冲突检测或删除事件。

### 12.4 服务端校验

- 客户端上传哈希用于声明预期内容。
- 服务端或对象存储必须根据收到的字节独立计算校验值。
- 校验失败时必须拒绝提交。
- 只有数据和元数据完成持久化后才能确认版本保存成功。
- 大文件应支持分片校验和断点续传。

### 12.5 加密注意事项

如果未来实施端到端加密，需要区分：

- 本地明文内容身份。
- 传输密文完整性。
- 服务端可见的密文哈希。

禁止在没有隐私评审时上传可用于跨用户判断相同明文的哈希。跨用户全局去重不属于首版目标。

## 13. 同步架构

### 13.1 同一同步引擎

手动和自动同步只能是两种触发策略：

```text
手动按钮 ─┐
保存成功 ─┤
恢复网络 ─┼→ 同步协调器 → 同步队列 → 相同 API/冲突规则
应用启动 ─┤
后台任务 ─┘
```

禁止维护两套数据格式、两套队列或两套冲突算法。

### 13.2 推送流程

1. 读取待同步队列。
2. 获取服务端当前版本摘要。
3. 比较 `baseRevision` 和远端版本。
4. 一致时提交版本清单。
5. 服务端返回缺失的块和附件哈希。
6. 客户端只上传缺失对象。
7. 服务端独立校验对象。
8. 在条件写入或事务中挂接新版本。
9. 成功后更新本地同步状态和游标。

### 13.3 拉取流程

1. 携带同步游标请求增量事件。
2. 获取新建、更新和删除事件。
3. 根哈希相同且历史关系已知时跳过正文下载。
4. 根哈希不同则获取版本清单和缺失块。
5. 有本地未同步草稿或版本时不得直接覆盖。
6. 应用远端变更后推进游标。

禁止通过每次下载全部笔记来检查变化。

### 13.4 冲突处理

第一阶段冲突策略：

- 保留本地草稿。
- 保留远端稳定版本。
- 阻止静默覆盖。
- 允许用户查看两者并选择保留方向。
- 同步其他无冲突笔记，不因单篇冲突阻塞全局队列。

后期可以增加：

- 不同块自动合并。
- 同一文字块的三方合并。
- 画布图层合并。
- 多设备共同编辑。

### 13.5 同步套餐建议

基础能力：

- 本地草稿自动保存。
- 手动同步。
- 基础的启动或前台低频同步是否免费，产品上线前复核。

付费扩展可以包括：

- 保存后快速自动同步。
- 更频繁的后台同步。
- 云端未保存草稿备份。
- 更多设备。
- 更长历史保留。
- 更大附件和云空间。

不得把本地数据安全能力作为付费限制。

### 13.6 移动端后台限制

Expo SDK 56 的后台任务由操作系统调度，不能保证准确或立即执行。Android 周期后台任务存在系统最小间隔，iOS 由系统决定实际启动时间。因此：

- 保存后需要快速同步时，应优先在前台执行。
- 后台任务只能作为补偿。
- UI 不得承诺精确的后台同步时间。
- 同步队列必须在下次启动时继续处理。

参考：[Expo SDK 56 BackgroundTask](https://docs.expo.dev/versions/v56.0.0/sdk/background-task/)。

## 14. 容量和笔记大小模块

### 14.1 两种大小

必须区分：

| 类型 | 用途 |
| --- | --- |
| 笔记逻辑大小 | 告诉用户当前笔记包含多少正文和引用资源 |
| 账户实际占用 | 进行云空间配额和计费 |

两篇笔记引用同一附件时，逻辑大小都可以包含该附件，但账户实际占用只计算一次。

### 14.2 本地大小计算

本地模块负责估算：

- 标题和版本清单的 UTF-8 字节数。
- 各块规范化负载大小。
- 当前笔记引用附件大小。
- 手写笔迹和画布图层数据。
- 预览缓存大小应单独显示，不计入云端逻辑正文。

本地估算用于提前提示，不是最终配额权威。

### 14.3 服务端配额

服务端负责最终计算：

- 当前版本唯一块。
- 历史版本新增的唯一块。
- 唯一附件。
- 云端草稿。
- 回收站和未过期删除数据。
- 必要的服务端派生文件。

服务端必须在事务或原子配额操作中防止并发上传突破限制。

### 14.4 暂定配额

| 项目 | 暂定值 |
| --- | --- |
| 免费账户云空间 | 3GB |
| 单附件 | 100MB |
| 单篇结构化正文 | 5～10MB，待压力测试 |
| 单图片原文件 | 待决策，可另生成压缩预览 |
| 历史保留 | 待产品和成本评审 |

100MB 是附件限制，不是整篇笔记限制。

### 14.5 用户界面

后期 UI 应提供：

- 当前笔记逻辑大小。
- 账户已用和总空间。
- 正文、附件、历史、草稿和回收站分类占用。
- 80%、95% 和 100% 阶段提示。
- 大附件、历史和回收站清理入口。

## 15. 画布块与图层系统

### 15.1 画布定位

画布是笔记流中的一种块：

```text
笔记
├── 文字块
├── 代码块
├── 画布块
│   ├── 背景层
│   ├── 图片层
│   ├── 手写层
│   ├── 图形层
│   └── 文本标注层
└── 文字块
```

首版不允许手写直接覆盖普通流式正文。原因是字体、宽度和换行变化会导致笔迹坐标错位。

### 15.2 CanvasBlock

画布块至少包含：

- `canvasId`。
- 固定逻辑宽高。
- 背景设置。
- 图层顺序清单。
- 视口默认设置。
- `schemaVersion`。
- `canvasRootHash`。

首版固定逻辑坐标不随设备像素直接变化，渲染时按视口缩放。

### 15.3 Layer

持久图层至少包含：

- `layerId`。
- `type`。
- `orderKey`。
- `visible`、`locked`。
- `opacity`。
- 平移、缩放、旋转变换。
- 类型负载或资源引用。
- `payloadHash`。
- `schemaVersion`。

选框、控制点、吸附线等交互覆盖层只属于 UI，不持久化、不进入版本哈希。

### 15.4 图层类型

| 类型 | 内容 | 首版 |
| --- | --- | --- |
| background | 纯色、网格、横线或背景资源 | 必须 |
| image | 图片资源引用和变换 | 必须 |
| ink | 矢量笔迹集合 | 必须 |
| shape | 线、箭头、矩形、圆形 | 后期 |
| text | 自由定位文字标注 | 后期 |

### 15.5 手写笔迹

每条笔迹应该保存：

- `strokeId`。
- 画笔类型。
- 颜色和粗细。
- 点序列。
- 每个点的逻辑坐标。
- 可选压力和时间信息。
- 笔迹边界框。

一次完整落笔通常形成一个撤销单元。橡皮擦策略必须在“整条笔迹删除”和“笔迹切割”之间做明确选择。

### 15.6 性能策略

- 只渲染可视区域或相关图层。
- 图片使用预览尺寸，编辑或导出时再读取原文件。
- 手写点数据避免每次移动都完整序列化画布。
- 可以生成画布预览缓存，但缓存不是权威数据。
- 资源引用变化和几何变换变化分开保存。
- 大型画布必须在低端 Android 真机验证内存、帧率和恢复速度。

## 16. 本地持久化

### 16.1 存储选择

核心笔记、草稿、版本、块、资源引用和同步队列应该使用支持事务和局部更新的本地数据库。AsyncStorage 可以继续保存少量设置、令牌或简单标识，但不应承载大型结构化笔记 JSON。

本项目已经选用并安装 Expo SDK 56 对应的 `expo-sqlite ~56.0.5`。Android、iOS 和 Web 共用同一迁移清单与数据库端口；Web 支持在 Expo SDK 56 中仍为 Alpha，必须启用 WASM 资源和跨源隔离响应头。

当前正式数据库名为 `irisnote.db`。应用启动时启用外键约束与 WAL，并在渲染业务 Provider 前完成迁移。初始化失败时禁止自动删除或重建正式数据库。

参考：[Expo SDK 56 SQLite](https://docs.expo.dev/versions/v56.0.0/sdk/sqlite/)。

### 16.2 概念表

阶段 1 当前只创建：

- `schema_migrations`：记录已应用迁移的版本、名称和时间。
- `PRAGMA user_version`：作为 SQLite 文件当前结构版本，与迁移登记表交叉核对。

后续阶段的本地数据库至少需要覆盖：

- notes
- note_revisions
- revision_blocks 或 revision_manifests
- blocks / block_contents
- edit_sessions
- draft_blocks
- assets
- asset_references
- sync_queue
- sync_state
- tombstones
- schema_migrations

草稿、版本、块、附件和同步表仍必须在各自实施阶段单独评审，不得直接照抄概念名称上线。

### 16.3 事务边界

以下操作必须事务化：

- 从完整草稿创建稳定版本并更新当前版本指针。
- 更新附件引用与引用计数。
- 创建删除墓碑并更新笔记删除状态。
- 应用一个服务端增量事件。
- 执行不可拆分的数据迁移步骤。

草稿块的高频保存可以使用更小事务，但必须保持顺序和原子性。

平台事务策略：

- Android、iOS 文件库显式打开独立连接，在事务外启用并确认外键后执行 `BEGIN IMMEDIATE`，结束后关闭；不直接使用先开启事务的 `withExclusiveTransactionAsync()`。
- Web 和内存库复用主连接，在外键确认后执行 `BEGIN IMMEDIATE`；应用数据库端口增加单一串行队列，禁止业务绕过端口直接访问原始 SQLite 实例。
- 同库初始化按实际路径串行，迁移版本必须在写锁内重新读取；最后一个资源租约释放后等待初始化和已接收任务完成再关闭，快速重挂载等待旧连接关闭。
- 所有来自业务数据的 SQL 参数必须通过绑定参数传入；`execAsync()` 只允许执行静态迁移和 PRAGMA 语句。

## 17. 资源与附件生命周期

### 17.1 导入

1. 用户选择文件。
2. 复制到应用控制的临时或正式目录。
3. 流式计算文件哈希和字节大小。
4. 校验类型和暂定大小限制。
5. 创建或复用账户内资源。
6. 创建块或图层引用。
7. 将资源加入上传队列。

### 17.2 引用与删除

- 删除图片块只删除引用，不应立即删除共享资源。
- 只有没有当前版本、历史、草稿和回收站引用时，资源才可进入清理候选。
- 清理应有延迟期，防止竞态和误删。
- 服务端与客户端都必须能够恢复中断上传。

### 17.3 去重范围

首版只允许同一账户内部按内容哈希去重。禁止在没有隐私设计的情况下实施跨账户全局去重。

## 18. 兼容现有业务

块化不能只完成编辑器，还必须逐项处理下游消费者。

### 18.1 查看器

- 根据块类型渲染。
- 未知块类型显示安全降级占位。
- 旧字符串笔记在迁移前仍能查看。

### 18.2 字数统计

- 保持本地计算，禁止为统计拉取服务端全文。
- 第一版可以按稳定顺序将可统计块转换为统一文本后复用现有规则。
- 后期可以按块哈希缓存统计结果并增量汇总。
- 代码、表格、图片和链接的现有识别语义需要明确如何映射到块类型。

### 18.3 搜索

- 建立可搜索文本投影。
- 图片说明、代码、画布文本层是否进入索引需要明确。
- 二进制附件内容搜索属于后期能力。

### 18.4 分享与导出

- TXT：输出可读纯文本并标记不可展开块。
- Markdown：将支持的块转换为 Markdown，资源单独导出。
- PDF/图片：按查看器布局渲染。
- 画布：渲染为图片或 PDF 区域。
- 未知第三方块：提供占位信息，禁止静默丢失。

## 19. 旧笔记迁移

迁移是独立阶段，禁止与大规模 UI 重写同时进行。

### 19.1 迁移目标

将现有：

```text
title + content:string
```

转换为：

```text
Note + Revision V1 + 基础块清单
```

### 19.2 迁移原则

- 迁移前保留原始标题和正文快照。
- 迁移过程具有明确 `migrationVersion`。
- 同一笔记重复执行迁移应得到相同结果或安全跳过。
- 迁移不得依赖网络成功。
- 迁移失败只影响当前笔记，不应破坏整个数据库启动。
- 迁移完成并验证前不得删除原始字段或备份。

### 19.3 第一版转换策略

最安全的第一步是将原始正文整体放入一个兼容文本块，而不是立即解析成大量 Markdown 块。等基础块存储和恢复稳定后，再提供可选的结构化拆分迁移。

### 19.4 回滚

- 保留可逆导出函数，将支持的基础块重新序列化为旧正文。
- 数据库升级失败时停止进入编辑器并保留只读访问或备份导出能力。
- 正式移除旧字段前必须经过至少一个稳定发布周期和真实数据验证。

## 20. 建议模块边界

以下只是目标组织建议，创建任何文件前仍需结合当时源码重新审计。

```text
src/core/editor/
├── components/
├── blocks/
├── commands/
├── selection/
├── undo/
├── canvas/
├── editor.types.ts
└── index.ts

src/features/notes/
├── components/editor/       # Notes 适配层；后续可按实际规模调整
├── editor/session/
├── drafts/
├── revisions/
├── storage/
├── sync/
├── assets/
├── quota/
└── migration/

src/features/excerpts/
└── editor/                  # Excerpts 需求明确后再创建适配层
```

职责规则：

- Screen 负责路由参数、页面级状态和组合。
- `core/editor` 负责可跨业务复用的输入状态、交互、块操作、选择区和撤销能力，不直接调用远端接口。
- Feature 编辑器适配层负责把 Note 或 Excerpt 转换为通用编辑器值，并接收编辑结果。
- Session 属于具体 Feature，负责编辑会话和保存协调。
- Drafts 负责本地草稿持久化。
- Revisions 负责版本清单、哈希和历史。
- Storage 负责数据库端口和事务。
- Sync 负责队列、游标和冲突。
- Assets 负责文件和引用生命周期。
- Quota 负责大小估算和服务端配额结果。
- 禁止为了目录完整提前创建空模块；只有真实职责出现时才增加 `blocks`、`commands`、`selection`、`undo`、`canvas` 或 Excerpts 适配文件。

## 21. 分阶段实施路线图

每个阶段都必须经过“只读审计 → 文件级计划 → 用户确认 → 实现 → 验证 → CHANGELOG”的项目变更流程。

### 阶段 0：冻结规范和基线

目标：把业务不变量、当前行为和性能基线固定下来。

任务：

- 确认本文档中的已确认、暂定和待决策项。
- 在 `src/core/editor` 提取不依赖 Notes 的纯文本编辑器外壳，由 Notes 适配层保留既有保存语义。
- 在笔记详情页顶部提供进入现有编辑路由的简易按钮。
- 为当前创建、查看、编辑、保存、分享和统计建立回归清单。
- 准备包含空笔记、长文本、Markdown、代码、图片语法和异常字符的测试样本。
- 记录当前 API 和服务端能力。
- 建立并持续维护 `项目编辑器进度.md`，记录操作、逻辑、架构、版本、精确时间和验证证据。

验收：

- 没有未标记的关键业务歧义。
- 后续模块拥有可验证的输入输出。
- 通用编辑器不依赖 Feature，Notes 的保存、缓存和事件行为保持不变。
- 静态、服务端和真机验证结果被明确区分。

目标：建立支持事务、版本迁移和局部更新的本地持久化层。

任务：

- 选择并接入本地数据库。
- 建立数据库初始化和迁移框架。
- 定义仓库接口和事务辅助能力。
- 建立故障注入和备份恢复测试。

- 已建立原生独占事务、Web 串行普通事务和统一参数绑定端口。
- 已提供显式开发开关控制的临时数据库诊断，覆盖重开持久化、迁移幂等、事务回滚和备份可读性。

- 保存后清空撤销边界。
- 实现历史查看和恢复的最小数据能力。

- 草稿保存不出现在历史中。
- 每次有效点击保存只产生一个版本。

### 阶段 4：基础块数据模型

目标：将稳定版本从字符串升级为基础块清单。

### 阶段 5：旧笔记迁移

验收：

- 相同内容在不同设备产生相同哈希。

### 阶段 7：手动增量同步

目标：先用用户可控入口验证同步协议。

验收：

- 共享附件不会重复计费。

### 阶段 9：附件和图片块

## 22. 验证体系

### 22.1 单元测试

- 规范化和哈希测试向量。
- 块操作和撤销/重做。
- 草稿防抖、最长等待和强制补写。
- 保存队列乱序保护。
- 版本创建和无变化判断。
- 容量计算和去重计费。
- 图层变换和笔迹序列化。

### 22.2 集成测试

- 编辑 → 退后台 → 重启 → 恢复。
- 编辑 → 保存失败 → 重试。
- 多设备基于相同版本保存。
- 多设备基于不同版本冲突。
- 上传中断和断点续传。
- 删除和墓碑传播。
- 旧笔记迁移、查看、统计和分享。

### 22.3 性能测试

必须建立可重复的设备和数据基线，不以主观“看起来流畅”代替：

- 超长纯文本。
- 大量小块。
- 少量超大块。
- 多张高分辨率图片。
- 长时间连续手写。
- 多层画布缩放和平移。
- 大量历史版本。
- 低端 Android 真机冷启动和恢复。

### 22.4 故障测试

- 数据库写入中断。
- 保存事务中断。
- 应用在防抖等待期间被终止。
- 哈希校验失败。
- 上传分片缺失或重复。
- 服务端成功但客户端未收到响应。
- 配额在并发请求期间被其他设备占满。

## 23. 可观测性与排错

编辑器核心日志应使用结构化事件，并避免记录用户正文。建议记录：

- sessionId、noteId、revisionId 的安全标识。
- 草稿写入开始、成功、失败和耗时。
- 脏块数量和合并任务数量。
- 保存阶段和失败点。
- 同步队列长度、重试次数和错误类别。
- 哈希校验失败对象类型。
- 迁移版本和失败原因。
- 容量计算来源。

禁止在生产日志中输出笔记正文、附件内容、认证令牌或加密密钥。

## 24. 安全与隐私

- 所有客户端输入在数据库和 API 层使用参数绑定或等价安全机制。
- 文件类型不能只相信扩展名。
- 资源下载必须执行用户权限校验。
- 分享和导出使用临时文件时必须有清理策略。
- 草稿可能比稳定版本更敏感，应纳入本地数据保护范围。
- 端到端加密实施前必须先设计密钥丢失、换设备和恢复机制。
- 服务端不得使用客户端哈希替代权限和所有权校验。

## 25. 主要风险

| 风险 | 后果 | 控制措施 |
| --- | --- | --- |
| 一次性重写编辑器、数据库和同步 | 难以定位数据丢失 | 严格按阶段实施 |
| 草稿与历史概念混用 | 历史膨胀或撤销跨界 | 独立数据模型和测试 |
| 旧异步写入覆盖新内容 | 用户最新输入丢失 | 串行队列、序号和最新状态补写 |
| 只用整篇哈希做增量同步 | 内容变化后仍上传整篇 | 块/附件哈希和版本清单 |
| 哈希相同就认为版本相同 | 历史关系丢失 | 保留 revisionId 和 parentRevisionId |
| 依赖后台任务保证实时同步 | 系统未调度导致延迟 | 前台优先、持久队列补偿 |
| 图层覆盖流式正文 | 换行后笔迹错位 | 画布块固定坐标 |
| 大型图片和手写数据常驻内存 | 卡顿或崩溃 | 预览、可视区域渲染和真机基准 |
| 迁移后立即删除旧正文 | 无法回滚 | 原始快照和稳定发布周期 |
| 账户配额只由客户端判断 | 可绕过或并发超限 | 服务端权威原子计量 |
