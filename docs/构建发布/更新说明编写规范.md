# 版本更新说明编写规范

本文件供 Agent 在生成 IRisNote 版本包更新说明时读取。目标读者是使用应用的普通用户：让他们知道更新后能做什么、哪里更方便、哪些问题得到修复。

CHANGELOG 面向开发维护；更新说明面向用户。可以参考日志，但必须先核实版本范围，再提炼和改写，不能直接复制技术记录。

## 1. 何时读取与执行

- 用户要求“生成当前版本更新说明”“写这个安装包的更新内容”等时，先读取本规范及根目录 AGENTS.md。
- 遵守项目现有文件修改确认流程；已确认的同一任务范围不重复请求确认。
- 生成文案不代表获准预留构建号、构建、上传、发布、提交或推送代码。这些操作遵循用户另行授权。

## 2. 先确定这次更新包含什么

1. 确认目标版本号、构建号（如已分配）、目标提交 SHA，以及对比的上一已发布版本及其提交。优先使用用户指定的安装包、发布记录和包旁的 `.apk.json` 元数据，并核对一致性。
2. 生成构建前草稿时，以准备发布的提交为目标。仅在明确要求总结工作区时纳入未提交改动，并标明这是待构建草稿，不能称为现有安装包内容。
3. `app.json` 的版本只能作为线索。发布命令接收单独的版本参数，同一版本号也可能有多个构建；不能仅凭配置版本、文件修改时间或 CHANGELOG 日期判定包内容。
4. 从上一已发布版本到目标提交的实际差异中筛选改动，结合对应 CHANGELOG、提交记录和必要的源码检查。日志中后续撤销、被替换的方案不重复写入；目标提交之后的改动不得写入。
5. 若是经确认的首次发布，介绍该包已具备的主要功能，不把全部开发历史写成“新增”或“修复”。
6. 如果目标包、提交或上一版本范围无法确定，先汇报缺失信息并询问用户。可以整理候选条目，但只能标记为待核实草稿，不能猜测发布范围或宣称已发布。

在给维护者的交付说明中记录目标版本、构建号、对比范围、目标 SHA、证据及未核实项。不要把这些内部核对信息混入给用户看的更新正文。

## 3. 筛选与合并规则

- 保留用户可以直接感受到的功能、操作、界面、可靠性和兼容性变化。
- 同一功能的多条日志合并为最终效果，优先写重要变化，不按开发时间堆砌。
- 排除纯重构、类型修复、测试调整、构建目录调整、依赖维护、文档和 Agent 规则修改。只有证据表明它们解决了具体用户问题时，才描述那个用户问题。
- 设计文档、计划、占位入口、禁用功能和未进入目标包的实现不能写成已上线功能。
- 涉及服务端、权限或平台支持的功能，要确认目标用户实际可用；必要时用一句通俗说明写清条件。
- 影响升级、数据保留或使用方式的已知限制必须保留。不要把“编译通过”或“单元测试通过”写成“所有设备运行正常”。
- 没有可确认的用户可见变化时，向维护者如实说明，不为凑条目虚构“性能提升”或“稳定性优化”。

## 4. 语言要求

- 使用自然、简短的中文，每条优先一句话，说清“哪里变了，以及现在能怎样使用”。
- 使用用户在界面上能看到的名称，如“笔记”“待办”“草稿”“同步”，不用函数名、文件路径、数据库字段、框架名或错误码解释变化。
- 新功能用“新增……”“现在可以……”；优化说明具体操作变化；修复说明发生场景和原来的问题。
- 不使用“赋能”“全面升级”“极致体验”等空话。没有实测依据，不写“更快”“更流畅”“大幅提升”，不编造百分比。
- 不扩大承诺范围：特定场景修复不能写成“解决所有同步问题”，新增权限入口不能写成“自动完成安装”。
- 默认保留最重要的 3～8 条，内容少时允许更少，重大更新可适当增加。重要升级提醒不受条数限制。

## 5. 输出结构与文件约定

正文依次使用“新增功能”“体验优化”“问题修复”，按需追加“升级提醒”；没有内容的分类直接省略。只有一两条时也可以直接列出，不必拆分类。

默认保存为 UTF-8 纯文本（.txt）文件，文件名只含版本号，不加构建号、draft 等任何附加词，沿用现有 `releases/notes-<版本号>.txt` 命名：

- `releases/notes-<版本号>.txt`；同一版本多次预留构建时复用同一文件，写入前检查已有内容，避免覆盖另一构建的文案。
- 用户指定路径时遵循其路径。

发布工具在 `reserve --notes <文件路径>` 阶段读取全文，之后才返回构建号。生成草稿不调用此命令。根目录新增说明文件也可能影响发布工具的工作区干净检查，应在实际发布任务中按用户授权处理，不能为消除检查而自动提交或删除。

应用更新弹窗目前把说明作为普通文本显示，因此正文使用普通标题、空行和 `-` 列表，不依赖 `#` 标题、加粗、表格、HTML、图片或链接渲染。不要把证据表、待办项和本规范一起传入 `--notes`。当前客户端限制说明为 12000 个 JavaScript 字符，提交发布前还应核对当时的实际限制。

以下仅为结构模板；生成时替换占位符并删除空分类，不把代码围栏写入正文：

```text
IRisNote <版本号> 更新说明

新增功能
- <新增能力及使用方式。>

体验优化
- <具体操作或界面的变化。>

问题修复
- 修复<具体场景>下<用户遇到的问题>。

升级提醒
- <仅填写已核实且用户需要知道的限制或操作。>
```

发布日期只在已确认时填写，不把生成日期当作发布日期。

## 6. 改写示例

以下只演示语言转换，不代表这些变化属于任何待发布版本。使用前必须按第 2 节核实。

| 开发记录表达                                     | 面向用户的表达或处理                                                   |
| ------------------------------------------------ | ---------------------------------------------------------------------- |
| 待办页挂载竖向周分页日期轨道，增加月历锚点气泡   | 待办日历移到了页面右侧，上下滑动即可切换周，也能打开月历快速选择日期。 |
| 草稿清理意图持久化到上传队列，执行任务时恢复清理 | 修复笔记保存后，草稿可能没有及时清理的问题。                           |
| withLayoutContext 保留完整属性类型，恢复回调推断 | 纯开发类型调整，不写入用户更新说明。                                   |
| 构建产物按版本号分目录存放                       | 开发发布流程调整，不写入用户更新说明。                                 |
| 新增待办创建弹窗设计文档，尚未实现               | 仍处于设计阶段，不写成新增功能。                                       |

## 7. 交付前检查

- [ ] 版本号、构建号、目标提交和对比范围有依据；未确定内容已单独说明。
- [ ] 每条变化实际包含在目标范围内，未混入未提交、已撤销或后续版本内容。
- [ ] 已过滤纯开发维护记录，合并同一功能的重复条目。
- [ ] 用普通用户能理解的语言描述具体变化，没有技术细节堆砌或无依据的效果承诺。
- [ ] 必要的平台限制、使用条件和升级提醒准确保留。
- [ ] 正文无占位符、空分类、内部证据、虚构发布日期或重复版本内容。
- [ ] 文件名、编码、正文长度及纯文本显示方式适合实际发布入口。
- [ ] 向维护者交付文件路径、版本范围与核实状态；没有把生成说明称为完成发布。

## 8. 后续调用示例

可以对 Agent 说：
