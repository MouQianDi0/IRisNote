## 0. 文档定位与边界

- **定位**：汇总 Android、iOS、鸿蒙（HarmonyOS NEXT）三平台的系统通知能力，按**普通通知 / 重要通知 / 动态通知**三类对照；汇总本项目现有通知需求与出处；给出渠道映射草案。**本文档不含任何实现。**
- **三层通知边界**（避免混淆）：
  1. **应用内横幅**（已实现，`src/core/notifications/`，见全局横幅规范）——纯 JS 层 UI，与系统通知无关，本文档**不改动**该层；
  2. **系统通知**（本文档主题）——零实现，需独立立项后开发；
  3. **邮件渠道**（`resend` 依赖，属验证码类邮件）与系统通知无关，不在本文范围。
- **结论先行（动态通知）**：三平台的"动态通知"准入（Android Live Updates 政策、iOS Live Activities 内容形态、鸿蒙实况窗场景审核）**均不含笔记/日历类应用场景**，Android 政策更点名禁止"即将到来的日历事件"使用 Live Updates。→ **本项目动态通知暂不立项**，仅保留 §5 的认知映射。

## 1. 三平台通知体系总览

### 1.1 按本文三分类的落地形态

| 分类 | Android（8.0+ / 16） | iOS（15+ / 16.1+） | 鸿蒙 HarmonyOS NEXT |
|---|---|---|---|
| **普通通知** | 渠道 importance `DEFAULT`（有提示音、无横幅）或 `LOW`（静默、仅图标） | interruptionLevel `active`（默认行为）/ `passive`（无声入列表，不打扰） | 渠道 `CONTENT_INFORMATION` / `OTHER_TYPES`（默认 LEVEL_MIN，静默）或 `SERVICE_INFORMATION` 调低 |
| **重要通知** | 渠道 importance `HIGH`（横幅 heads-up + 提示音 + 振动）；**无更高等级** | interruptionLevel `timeSensitive`（时效性，突破专注模式/定时摘要）；`critical`（需 Apple 特批 entitlement，穿透静音） | `SERVICE_INFORMATION` / `SOCIAL_COMMUNICATION` 默认 LEVEL_HIGH（横幅 + 提示音；横幅最终以用户设置开关为准） |
| **动态通知** | 前台服务常驻通知（MediaStyle/导航等）+ **Android 16 Live Updates**（QPR1 起完整生效） | **Live Activities**（灵动岛 + 锁屏实时活动，ActivityKit，16.1+） | **实况窗 Live View Kit**（状态栏胶囊 + 锁屏/通知卡片，HarmonyOS 5+） |

### 1.2 渠道概念映射

| 概念 | Android | iOS | 鸿蒙 |
|---|---|---|---|
| 开发者建"渠道" | `NotificationChannel`，**任意数量、自定义 ID/名称/图标** | **无用户可见渠道**；按通知携带 Category（动作组）、`threadIdentifier`（分组）、`interruptionLevel`（分级） | `NotificationSlot`，**固定系统枚举 7 类，不可自建任意命名渠道** |
| 分级档位 | importance 5 档（NONE/MIN/LOW/DEFAULT/HIGH） | interruptionLevel 4 档（passive/active/timeSensitive/critical） | SlotLevel 5 档（NONE/MIN/LOW/DEFAULT/HIGH） |
| 分级归属 | **渠道级**（建渠道时定死，建后 App 改不动） | **单条通知级**（每条通知自带） | 渠道类型映射默认级别，可经 `addSlot` 调整，用户设置优先 |
| 用户控制粒度 | 每渠道：声音/振动/横幅/锁屏/角标全可改 | 每 App：锁屏/横幅/声音/标记/预览/时效性整体开关 | 每渠道类型 + 每应用：横幅/声音等在 设置>通知和状态栏 |

## 2. Android：通知渠道（NotificationChannel）

### 2.1 渠道模型

- API 26+ 通知**必须**挂渠道；App 可创建任意数量的 `NotificationChannel`（自定义 ID、用户可见名称、描述、图标，可用 `ChannelGroup` 分组）。
- 渠道创建时可设置：importance、声音（含 `audioAttributes`）、振动样式、呼吸灯、锁屏可见性、角标、`bypassDnd` 等；**创建后 App 再改 importance 会被系统忽略**（只能换新渠道 ID 迁移，且用户对该渠道的设置随之丢失）。
- 用户在系统设置中可覆盖渠道的一切属性（降级、关声音、关横幅），App 只能读（`getNotificationChannelAsync`）不能写。
- Android 13+：`POST_NOTIFICATIONS` 运行时权限，未授权则一切通知不显示。

### 2.2 普通通知

| importance | 行为 | 适用 |
|---|---|---|
| `LOW`（2） | 无声、无横幅，仅状态栏图标+下拉列表 | 同步结果、后台任务完成等低打扰事件 |
| `DEFAULT`（3） | 有提示音，无 heads-up 横幅 | 一般服务消息、公告 |

### 2.3 重要通知

- `HIGH`（4）= **Android 第三方应用的打扰上限**：heads-up 横幅 + 提示音 + 振动。
- **没有 iOS critical 那样的穿透等级**：`bypassDnd` 对第三方应用基本无效，勿打扰模式下无法保证送达；"重要"最终由用户对渠道的设置决定。
- 长按通知可直达渠道设置，用户可把 HIGH 一键降成静音——设计上应把"重要"用于少数渠道，而非单条通知。

### 2.4 动态通知

两种形态：

1. **前台服务常驻通知**（传统形态）：`MediaStyle`、通话 `CallStyle`、导航类 FGS 的进度通知，`setOngoing(true)` 不可滑删，系统级保障存活。适合"正在进行的任务"，但展示形态仍是普通通知卡片。
2. **Live Updates**（Android 16 引入、QPR1 起完整生效，对标 iOS 灵动岛）：通知被"提升（promoted）"到抽屉顶部置顶、锁屏常驻、状态栏**胶囊 chip**（最大宽 96dp，可含图标+短文本+倒计时），默认展开、不可折叠，用户可临时收起或降级为普通通知。

**Live Updates 硬性要求**（全部满足才可被提升）：

| 项 | 要求 |
|---|---|
| 样式 | Standard / BigTextStyle / **CallStyle** / **ProgressStyle**（新，进度段+节点+计时器）/ MetricStyle |
| 权限 | Manifest 声明 `android.permission.POST_PROMOTED_NOTIFICATIONS`（安装级，非运行时）；用户总开关可用 `canPostPromotedNotifications()` 查询 |
| 请求提升 | `setRequestPromotedOngoing(true)`（或 `EXTRA_REQUEST_PROMOTED_ONGOING`）+ `setOngoing(true)` + 必须有 `contentTitle` |
| 禁止项 | 自定义 RemoteViews 布局、group summary、`setColorized(true)`、渠道为 `IMPORTANCE_MIN` |
| 政策准入 | 必须是**用户主动发起、正在进行、全程需要关注**的"旅程"（导航、通话、打车/外卖跟踪） |
| 政策禁止 | **广告/促销、聊天消息、普通提醒、即将到来的日历事件**、功能快捷入口（此类应使用 Widget/快捷设置磁贴） |
| 生命周期 | 任务结束必须立即转普通通知或撤下；被用户降级后**禁止**重发提升通知（违规会导致权限被回收） |
| 其他 | target SDK 36；各 OEM 可附加准入条件 |

### 2.5 自定义程度评估

- **渠道维度自由度三平台最高**：任意命名/图标/数量、渠道级声音+振动样式+呼吸灯+锁屏策略。
- **代价是"创建即写死"**：importance 与声音等一旦发布不可修改，迭代需换渠道 ID 并承接用户流失。
- 用户主权最高：每渠道全属性可改；OEM（HyperOS/ColorOS 等）还会叠加自启动、通知分类等管控层，真机表现需按 [adb-layout-dump] 流程实测。

## 3. iOS：无渠道模型，分级随单条通知走

### 3.1 模型

- 授权制：`requestAuthorization` 一次性申请（alert/sound/badge/**timeSensitive**/provisional/providesAppNotificationSettings 等选项）；系统设置里用户按 **App 粒度**控制（锁屏/横幅/声音/标记/显示预览/分组），**没有渠道级 UI**。
- App 侧组织手段：`UNNotificationCategory`（长按/下拉的动作按钮组，可含文本输入）、`threadIdentifier`（会话分组折叠）、`relevanceScore`、自定义声音（打包内 ≤30s）、Notification Service Extension（送达前解密/下载附件）。

### 3.2 普通通知

- `active`：默认，正常横幅+声音。
- `passive`（iOS 15+）：无声、无横幅、无触感，仅出现在通知列表/锁屏——适合"同步完成""已保存"类回执。

### 3.3 重要通知

- `timeSensitive`（时效性）：需 App 具备 **Time Sensitive Notifications capability** 并在授权时包含 `timeSensitive` 选项；显示黄色"时效性"标签，**可突破专注模式（含勿打扰）与定时推送摘要**；用户可在设置中整体关闭该能力。Apple 明令禁止用于营销/促销。
- `critical`（关键警报）：需向 **Apple 单独申请 entitlement**（医疗、安防、无障碍等特定品类），可穿透静音键与勿打扰、强制音量。**笔记类应用不可能获批 → 本项目不做**。

### 3.4 动态通知：Live Activities

- iOS 16.1+，ActivityKit 启动/更新/结束；展示于**灵动岛**（iPhone 14 Pro 起）与**锁屏卡片**，锁屏后仍持续更新。
- 更新途径：App 进程内直接更新；或 APNs 推送（push type `liveactivity`，设备级 token，`timestamp`/`staleDate` 携带）。**推送更新有动态预算限频**，只适合分钟级以上粒度，不适合秒级刷新。
- 生命周期：活跃最长 **8 小时**（此后系统强制结束、仅保留锁屏展示），**12 小时**后彻底移除。
- 支持锁屏卡片上的按钮交互（App Intents）；内容需为"持续变化的实时数据"（进度、比分、配送位置）。

### 3.5 自定义程度评估

- **通知本体**自定义强：附件、动作按钮、分组、声音（≤30s）、Service Extension 二次加工。
- **渠道维度无**：分级、声音意图由每条通知自带；`critical`/`timeSensitive` 需 Apple 侧 capability/entitlement 门槛。
- 策略空间：`provisional` 静默授权（先静默送达、在通知列表里让用户升级为正式授权）适合提醒类场景的弱打扰起步。

## 4. 鸿蒙 HarmonyOS NEXT：固定渠道 + 实况窗白名单制

### 4.1 模型（Notification Kit）

- `notificationManager.publish(request)` 发布；`request.notificationSlotType` 指定渠道（**渠道不存在会按默认配置自动创建**；社区经验：务必把 slotType 写进 request，仅 `addSlot` 不保证生效）。
- 授权：`requestEnableNotification(context)` 拉起系统弹窗——**每个应用只弹一次**，用户拒绝后无法再弹，需 `openNotificationSettings`（API 13+）引导去设置；`isNotificationEnabled(Sync)` 查询状态。
- **渠道是系统固定枚举，第三方不能自定义命名渠道**（与 Android 最大的差异）。

### 4.2 SlotType 枚举（渠道类型 × 默认级别）

| SlotType | 值 | 含义 | 默认 SlotLevel | 备注 |
|---|---|---|---|---|
| `UNKNOWN_TYPE` | 0 | 未知 | LEVEL_MIN | |
| `SOCIAL_COMMUNICATION` | 1 | 社交通信 | **LEVEL_HIGH**（横幅+提示音） | 面向 IM 类；笔记应用不宜占用 |
| `SERVICE_INFORMATION` | 2 | 服务提醒 | **LEVEL_HIGH**（横幅+提示音） | **本项目提醒类的正确落点** |
| `CONTENT_INFORMATION` | 3 | 内容资讯 | LEVEL_MIN（静默） | 低打扰回执类 |
| `LIVE_VIEW` | 4（API 11+） | 实况窗 | LEVEL_DEFAULT | **三方应用不可直接创建**，见 §4.4 |
| `CUSTOMER_SERVICE` | 5（API 11+） | 客服消息 | LEVEL_DEFAULT | 需用户主动发起会话 |
| `OTHER_TYPES` | 0xFFFF | 其他 | LEVEL_MIN | 兜底 |

SlotLevel 档位：`LEVEL_NONE`(0) 关闭 / `LEVEL_MIN`(1) 无图标无声 / `LEVEL_LOW`(2) 有图标、无横幅无声 / `LEVEL_DEFAULT`(3) 有图标+提示音、无横幅 / `LEVEL_HIGH`(4) 有图标+**横幅**+提示音。横幅展示最终以用户在 设置>通知和状态栏 的开关为准。

### 4.3 普通 / 重要通知

- **普通**：`CONTENT_INFORMATION` / `OTHER_TYPES`（默认静默入通知中心），或将 `SERVICE_INFORMATION` 经 `addSlot` 调低。
- **重要**：`SERVICE_INFORMATION`（默认 LEVEL_HIGH = 横幅+提示音），即鸿蒙上"重要通知"不需要像 Android 那样建专属渠道，**选对渠道类型即得默认强度**；强度上调空间止于 LEVEL_HIGH，无 critical 等价物，勿打扰穿透受系统/用户管控。

### 4.4 动态通知：实况窗（Live View Kit）

- 展示形态：状态栏**胶囊**（灵动岛式）+ 锁屏/通知卡片 + 沉浸态（地图、计时等富内容）；系统应用（通话/闹钟/录音/计时等）与三方应用两套体系，**三方需走 Live View Kit**（`liveViewManager.startLiveView`），`LIVE_VIEW` 渠道由**系统代理创建**，三方只能按同 ID 发布更新。
- **场景准入（白名单制）**：须满足时段性（明确起止）、时效性（信息只在特定时段有价值）、变化性（内容持续更新）；官方 11 类模板场景：即时配送、打车、航班、高铁、排队叫号、赛事比分、导航、计时、共享租赁、取餐、运动锻炼——**无笔记/日历类场景**。
- 接入门槛：AppGallery Connect「项目设置>开放能力管理」**申请实况窗权限**（按场景审核，需符合实况窗设计规范）；用户侧还需在 设置>通知和状态栏 开启实况窗显示。
- 生命周期：单个实况窗**最长 8 小时**（超时系统强制结束）；6.1.1(24) 起可用 `aliveTime` 自动关闭；系统要求及时更新保证时效。
- 更新方式：本地更新依赖应用进程存活，**官方推荐 Push Kit 推送更新**；HarmonyOS 5+，仅 Phone/Tablet。

### 4.5 自定义程度评估

- 三平台**最受限**：渠道不可命名/不可自由创建，级别由渠道类型映射；通知内容（文本/图片/多行/进度条）本身可自定义。
- 实况窗形态最像 iOS 灵动岛，但准入是**审核制**而非开发者自治，笔记类应用无法使用。

## 5. 横向对比与自定义程度总表

| 维度 | Android | iOS | 鸿蒙 NEXT |
|---|---|---|---|
| 渠道模型 | 任意自建渠道（Android 最自由） | 无渠道，分级随单条通知 | 固定 7 类系统枚举 |
| 分级 | 渠道级 importance（建后锁死） | 单条 interruptionLevel | 渠道类型映射 SlotLevel |
| 重要级打扰上限 | HIGH（heads-up） | timeSensitive / critical（特批） | LEVEL_HIGH（横幅+提示音） |
| 穿透勿打扰 | 第三方不可 | timeSensitive 可（用户可关）；critical 可 | 受系统/用户管控，无保证 |
| 动态形态 | FGS 常驻 + Live Updates（QPR1+） | Live Activities（16.1+） | 实况窗（HarmonyOS 5+） |
| 动态准入 | 开发者自治 + 政策约束（禁日历事件/广告） | 开发者自治（需持续变化内容） | **AGC 场景白名单审核** |
| 动态时长上限 | 任务结束即止 | 活跃 8h / 移除 12h | 8h（aliveTime 可自动关） |
| 声音自定义 | 渠道级，任意音频+audioAttributes | 单条，打包内 ≤30s | 渠道属性可设，系统声为主 |
| 授权机制 | 13+ 运行时权限 | 一次性授权（含 timeSensitive 选项） | 弹窗仅一次，拒绝后引导设置 |
| 用户控制粒度 | 每渠道 | 每 App（+时效性总开关） | 每渠道类型+每应用 |
| OEM/厂商变数 | 高（国内 ROM 叠加管控、无 FCM） | 无 | 低（华为统一） |

**对本项目的含义**：同一业务语义需要三套落地——"提醒类"在 Android 走 HIGH 渠道、在 iOS 走 timeSensitive/active、在鸿蒙走 `SERVICE_INFORMATION`；"回执类"在 Android 走 LOW、iOS 走 passive、鸿蒙走 `CONTENT_INFORMATION`。**不存在三平台统一的渠道抽象**，只能以"业务语义 → 各平台映射"表驱动。

## 6. IRisNote 通知需求汇总（现状与出处）

### 6.1 实现现状：系统通知零实现

- `package.json` **无任何通知/推送依赖**（无 expo-notifications/notifee/firebase/极光）；`android/`、`app.config.ts` 无 `POST_NOTIFICATIONS`、推送 SDK 等任何配置。
- 已实现的 `src/core/notifications/`（8 个文件 + 回归测试）是**应用内全局横幅**（banner.show/resolve + critical 优先级 + until-resolved 生命周期），不触碰系统通知。
- 唯一用户可见痕迹：`src/features/settings/screens/SettingsScreen.tsx:224-262`——概览卡显示"通知：站内"，"通知设置"行为 **disabled 占位**（value="规划中"，描述"当前站内提示由业务状态自动触发"）。

| 3 | 服务端"消息推送"扩展 | `docs/API后端/IRisNote 服务端部署手册（Docker 生产版）.md` §19 未来扩展 | 远期 |
| 4 | AI 日程/排期愿景（"/日历 命令 + AI 日程"，"下个工作日""避开假期"类指令） | `docs/学习参考/节假日数据源调研与选型.md` L140-156 | 业务愿景，是**提醒类通知**最可能的数据来源 |
| 5 | 日历组件首版**不做**日程/agenda | `docs/UI/日历公共组件规范.md` L17（"出现需求时另行立项扩展"） | 负向约束：日程提醒非近期 |
| 6 | 应用内横幅体系（已实现）与系统通知并行分层 | `docs/UI/全局横幅通知设计与调用规范.md`（"系统权限弹窗等系统界面不在应用层级保证范围内"） | 分层依据 |

**排除的干扰语义**（调研时勿混淆）：编辑器架构文档中的"增量推送"= 数据同步；事件总线/Zustand listener = 代码订阅；验证码 60s 倒计时 = 应用内计时。

### 6.3 分层结论

- 前台使用中的提示 → 应用内横幅（已有体系，继续用）；**后台/杀进程后仍需触达**（提醒到期、远期服务端推送）→ 系统通知，二者并行不互替。
- 当前无任何一条需求达到"必须立刻立项系统通知"的强度；最可能的第一个场景是**笔记/日程提醒**，且依赖日程数据模型先落地（日历组件首版不做日程）。

## 7. 适配方案草案（渠道映射 + Expo 落点）

### 7.1 预设渠道映射表（拟）

| 业务语义（拟） | Android 渠道（importance） | iOS（interruptionLevel） | 鸿蒙（slotType） | 说明 |
|---|---|---|---|---|
| **提醒**（笔记/日程到期） | `reminders` — **HIGH** | `active`；用户在设置页开启"时效性"后升 `timeSensitive` | `SERVICE_INFORMATION`（默认即 HIGH 横幅） | 到期即横幅；三平台各自的"重要"上限 |
| **回执**（同步完成/保存结果，后台触达时） | `sync` — **LOW** | `passive` | `CONTENT_INFORMATION`（默认 MIN 静默） | 低打扰；多数场景仍由应用内横幅承担 |
| **服务端消息**（远期 irisapi 推送） | `general` — DEFAULT | `active` | `SERVICE_INFORMATION`（经 addSlot 调 DEFAULT/LOW） | 远期立项时再细化 |
| **动态**（—） | 不适用 | 不适用 | 不适用 | 无合规场景，不立项（见 §0） |

### 7.2 Expo SDK 57 落点（立项时的技术底座）

- **expo-notifications 需先安装**（当前未安装）。SDK 57 已核实能力：
  - Android 渠道全套 API：`setNotificationChannelAsync(channelId, { name, importance, sound, vibrationPattern, enableVibrate, enableLights, lightColor, bypassDnd, lockscreenVisibility, showBadge, ... })`；注意 **importance 建后不可改**，渠道 ID 一次定准。
  - iOS `interruptionLevel` **直接支持** `'passive' | 'active' | 'timeSensitive' | 'critical'`（后两者还需 capability/entitlement）。
  - 本地调度：`scheduleNotificationAsync` + `SchedulableTriggerInputTypes`（DATE/DAILY/WEEKLY/CALENDAR…），提醒类纯本地通知即可覆盖，不依赖推送服务。
  - 自定义声音需在 app.config 通过 config plugin `sounds` 数组注册。
  - Android 推送（若远期接 expo push）**SDK 53 起必须 dev build**，Expo Go 不可用。
- **Live Activities 不在 expo-notifications 能力内**，需第三方库 + config plugin（本项目暂无场景，仅记录）。
- **鸿蒙无 Expo 构建目标**：鸿蒙列按 §4 记录的纯能力调研处理；若未来做鸿蒙端，需 react-native-harmony 适配层或原生实现，届时渠道映射直接查 §7.1 表。

### 7.3 权限申请时机（拟）

- 三平台共同原则：**场景触发时申请，不在首启冷弹**。首个真实场景（提醒保存时）弹授权；Android 13+ `POST_NOTIFICATIONS`、iOS `requestAuthorization`（提醒场景可含 `timeSensitive` 选项）、鸿蒙 `requestEnableNotification`（**仅一次机会**，拒绝后走 `openNotificationSettings` 引导——文案需预设）。
- 接入设置页时按 [后续开发指南](../架构指南/后续开发指南.md) §14 落位（settings-storage + 子页面），替换 `SettingsScreen` 现有 disabled 占位。

### 7.4 风险清单

| 风险 | 影响 | 对策 |
|---|---|---|
| Android 14+ 精确闹钟收紧（`SCHEDULE_EXACT_ALARM` 默认拒发，`USE_EXACT_ALARM` 限闹钟/日历品类） | 提醒可能延迟数分钟 | 提醒立项时评估：容忍 inexact 或声明权限+设置引导 |
| 用户随时可降级渠道/关时效性 | "重要通知"不保证横幅 | 提醒兜底 = 到期时刻若 App 在前台，叠加应用内横幅 |
| 国内 Android 无 FCM，OEM 推送 SDK 各异 | 仅影响**远期服务端推送**（§6.2-3），本地提醒不受影响 | 远期立项时再评估厂商通道/聚合服务 |
| 鸿蒙授权弹窗仅一次 | 拒绝后永远要靠引导 | 首弹文案谨慎；设置页提供"去开启"入口 |
