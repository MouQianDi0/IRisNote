# 节假日数据源调研与选型

> 调研日期：2026-09-16 · 调研方式：开放 API 实调 + npm 包本地实测（Node 跑通）+ GitHub/npm 元数据核对
> 结论：全球覆盖选 **date-holidays**（206 国本地规则引擎），中国放假安排必须叠加**中国专项数据**（chinese-days，与 holiday-cn 同源）；三家云端 API（Nager.Date / Calendarific / Abstract）都不适合做客户端主力，至多做服务端补充。

## 0. 结论速览

| 需求层 | 选型 | 理由 |
|---|---|---|
| 中国（首发优先级） | **chinese-days**（npm，离线） | isWorkday / 调休 / 农历 / 24 节气实测全对，数据与 holiday-cn 同源 |
| 全球覆盖 | **date-holidays**（npm，离线规则引擎） | 206 国、规则推导可算未来年份、州/省细分支持；中国"放假安排"缺失，不单独承担中国 |
| 数据更新通道 | **holiday-cn**（GitHub 数据集） | 国务院公告每日自动抓取，MIT，覆盖 2007–2027，可作远程 JSON 更新源 |
| 云端备选（暂缓） | Nager.Date 自部署 | 免费无 key、开源可自部署（.NET/Docker），但中国数据基本不可用 |
| 不推荐 | Calendarific / Abstract / timor.tech / chinese-workday | 免费额度撑不住逐日渲染 / 无差异化 / Cloudflare 反爬拦截程序访问 / npm 包打包损坏 |

**关键实测事实（本次调研最重要的一条）**：所有全球性数据源都不知道中国的「放假安排」——

- date-holidays 给出的 2026 春节只有 2/16–2/18 三天；国务院实际安排休 2/15–2/23（9 天），2/14、2/28（周六）补班；
- 2026 国庆 date-holidays 只有 10/1–10/3；实际休 10/1–10/7，且 9/20（周日）、10/10（周六）为调休补班日；
- Nager.Date 的 CN 2026 只有 6 条单日节日（元旦/春节/劳动节/端午/中秋/国庆各 1 天）。

→ 全球库只能给"节日名和日期"，给不了"哪天休假、哪天补班"。中国用户的刚性需求恰恰是后者，所以中国专项数据不是可选项。

## 1. 需求与约束（IrisNote 场景）

- **全球日历组件**：AppCalendar / AppCalendarList 规范已定（`docs/UI/日历公共组件规范.md`），UI 层技术路线 B（flash-calendar）已安装；数据层需要按日打点的节假日来源。
- **/日历 命令 + AI 日程**：AI 排期需要判断"某天是否工作日"，需要统一、可编程的查询接口而非网页数据。
- **Local-first**：节假日查询必须离线可用，不能把逐日渲染押在云端 API 上。
- **RN / Expo SDK 57**：包体积与 Metro 打包兼容性是硬约束。
- **中国用户第一优先级**：调休/补班准确性是刚需，其余国家允许精度渐进。

## 2. 逐源实测

### 2.1 date-holidays —— 全球本地规则引擎 ★ 全球主力

| 项 | 值（2026-09-16 核对） |
|---|---|
| npm | `date-holidays` v3.36.1，unpacked 10.97 MB |
| 依赖 | lodash、prepin、js-yaml、date-holidays-parser（纯 JS，包内无 `require("fs")` 等 Node 内置模块，Metro 无硬伤） |
| 协议 | ISC + CC-BY-3.0（数据部分） |
| 仓库 | commenthol/date-holidays，1101★，最近推送 2026-09-06（活跃） |

**实测（Node 跑通）**：

- 支持 **206 个国家/地区**；`US-TX` 州级 2026 有 31 条（细分到一级行政区）。
- CN 2026 返回 15 条：元旦、春节 2/16–18、妇女节（12:00 半天）、清明、劳动节、青年节（半天）、儿童节、端午、建军节（半天）、中秋 9/25、国庆 10/1–3。
- **2027 可直接计算**（规则推导，不依赖公告数据），2026/2027 条数一致。
- `isHoliday(new Date('2026-10-01'))` 返回完整对象（含 UTC start/end）；**注意它以 `Date` 对象交互，存在时区表述成本**——接入时建议在适配层统一转成 Date ID 字符串（与 FlashCalendar 的 `"YYYY-MM-DD"` 契约一致）。

**优点**：离线、规则引擎（历史年份与未来年份都能算）、国家/地区覆盖第一梯队、i18n 节日名。
**缺点**：① 中国"放假安排"完全缺失（见 §0）；② 全量 10.97 MB，直接进 RN bundle 不可接受；③ 中国条目含妇女节/青年节等"部分人群放假"噪声，UI 需过滤。
**RN 适配两条路线**：
- **方案 A（推荐）构建期生成**：Node 脚本跑 date-holidays，把目标国家的年份区间（当年+次年）生成精简 JSON（`{date, name, type}`），作为 app 资产按国家懒加载。运行时零依赖、体积可控，最符合 Local-first。
- 方案 B 运行时直接引用：需先实测 Metro 打包后真实体积再决定（其 `exports` 含 `./data` 子路径导出，理论上可按国家引数据，但**未实测**，标注为待验证）。

### 2.2 Nager.Date —— 免费开放 API，可自部署的云端备选

**实测 API**：

- `GET /api/v3/AvailableCountries` → **204 国**（原表"200+"基本准确）。
- `GET /api/v3/publicholidays/2026/CN` → 仅 **6 条单日**：元旦、春节、劳动节、端午、中秋、国庆各 1 天，无连休区间、无调休。中国场景基本不可用。
- 免 key、无认证、JSON 简洁；部分国家支持一级行政区。

| 项 | 值 |
|---|---|
| 仓库 | Nager/Nager.Date，1410★，MIT，最近推送 2026-09-15（非常活跃） |
| 形态 | .NET / REST API / Docker / NuGet，官方描述支持在线与离线使用 |

**定位**：客户端不直连（离线 ✗ + 中国 ✗）。若未来做服务端数据管道（如服务端统一聚合各国数据下发），它是成本最低的自部署来源。

### 2.3 Calendarific —— 数据最全的商业 API

- 官网口径：230+ 国家、地区级假期；**免费档 500 请求/月**（官网 pricing 确认），付费 $10/月起，约 1 请求/秒限速。
- 日历是逐日渲染场景：免费额度连一个中等活跃用户的月视图都撑不住，除非做"服务端缓存 + 全量下发"架构。
- **定位**：仅当未来需要 3300+ 地区长尾数据（如某国某个州的州假日）且愿意付费时，作为服务端 enrichment 的候选。客户端不碰。

### 2.4 Abstract Holidays API —— 商业 API，无差异化优势

- 官网口径：200+ 国家与地区、100 年数据；免费档约 1000 请求/月（第三方称免费档可能只返回往年数据，**未注册实测**）；付费约 $17/月起。
- **定位**：与 Calendarific 高度重叠，无独有优势，不推荐。

### 2.5 中国专项数据源 ★ 中国主力

#### holiday-cn（GitHub 数据集，事实标准）

- NateScarlet/holiday-cn，**2.1k★，MIT**，GitHub Actions **每日自动抓取国务院公告**，数据变化自动发 Release。
- 数据契约（实测 2026.json）：`{ year, papers: [国务院公告链接], days: [{ name, date, isOffDay }] }`，`isOffDay: false` 即补班日；另提供 `.ics` 订阅文件；覆盖 2007–2027。
- 实测 2026 四季度真值：中秋 9/25–27 休；国庆 10/1–7 休；**9/20（周日）、10/10（周六）补班**。
- 价值：它就是"国务院口径"的机器可读版。chinese-days 的数据与之同源。可作为 app 内**每年一次的远程 JSON 更新源**（每年 11 月公告发布后拉取替换）。

#### chinese-days（npm，推荐直接用）

| 项 | 值（2026-09-16 核对） |
|---|---|
| npm | `chinese-days` v1.5.9，unpacked 623 KB，MIT |
| 仓库 | vsme/chinese-days，1292★，最近推送 2026-07-07（维护中） |
| 入口 | CJS `dist/index.min.js` + ESM `dist/index.es.js` + 完整 TS 类型 |

**实测（Node 跑通，与 holiday-cn 真值逐项对照）**：

- `isWorkday('2026-10-01')` → false；`isWorkday('2026-10-03')` → false；`isWorkday('2026-10-10')` → **true（补班周六，正确）**；`isWorkday('2026-10-11')` → false（普通周日）。
- `getHolidaysInRange('2026-10-01','2026-10-08')` → 10/1–10/7，与公告一致。
- 全部导出：`isWorkday / isHoliday / isInLieu（是否调休）/ getDayDetail / getHolidaysInRange / getWorkdaysInRange / findWorkday`，**附赠农历公历互转（getLunarDate 等）、24 节气（getSolarTerms 系列）、闰月查询**——对中文日历是白赚的能力。

#### 反面样本（实测排除）

- **chinese-workday**（npm v2.0.0，61★）：`require()` 直接抛 `ReferenceError: exports is not defined`（package.json `type: module` 与 CJS 产物扩展名冲突的打包缺陷）。排除。
- **timor.tech API**（社区免费 API）：程序化请求被 Cloudflare 人机校验页拦截（`Just a moment...`），作为程序数据源不可靠。排除。

## 3. 横向对比（含实测值勘误）

| 数据源 | 覆盖 | 地区级 | 中国调休/补班 | 离线 | 费用 | 实测结论 |
|---|---|---|---|---|---|---|

| Calendarific | 230+ 国（官网口径） | ✅ 3300+ 地区 | ❌ | ❌ | 免费档 500 次/月，$10/月起 | 付费长尾候选，暂缓 |
| Abstract Holidays | 200+ 国（官网口径） | ✅ | ❌ | ❌ | 免费档约 1000/月，$17/月起 | 无差异化，不推荐 |

## 4. 推荐架构：本地双源 + 每年更新

```
┌─ 日历 UI（AppCalendar / flash-calendar，Date ID 契约）
│
├─ HolidayProvider（统一查询接口，全部离线）
│    ├─ 中国：chinese-days（isWorkday / isInLieu / 农历 / 节气）
│    └─ 全球：date-holidays 构建期生成的精简 JSON（当年+次年，按国家懒加载）
│
├─ 数据更新通道（每年一次）
│    └─ 每年 11 月国务院公告发布 → holiday-cn 自动跟进
│       → app 经应用内更新/远程 JSON 拉取替换中国数据与各国当年 JSON
│
└─ 云端（暂缓，仅当需要地区级长尾）
     └─ Nager.Date 自部署 或 Calendarific 付费档
```

统一接口草案（/日历 命令与 AI 日程都消费这一层）：

```ts
interface DayInfo {
  isOffDay: boolean;        // 是否休息日（含周末与法定假）
  isStatutory: boolean;     // 是否法定节假日
  isInLieu?: boolean;       // 是否调休（连休拼出来的）
  name?: string;            // 节日名
  source: 'china' | 'global';
}
interface HolidayProvider {
  getDayInfo(dateId: string, region?: { country: string; subdivision?: string }): DayInfo | Promise<DayInfo>;
  getYearDays(year: string, region?): Promise<Record<string, DayInfo>>; // 供日历打点
}
```

- **AI 日程**：排期时先查 `getDayInfo().isWorkday 语义`（chinese-days 的 isWorkday 已含补班判断），"下个工作日""避开假期"类指令直接可用。
- **日历 UI**：`getYearDays` 输出映射到 AppCalendar 日期格的节假日角标（对应《日历公共组件规范》的七态样式中的数据来源）。
- **更新运维**：每年 11 月盯一次公告（holiday-cn 的 Release 通知可订阅），确认 app 数据更新链路跑通即可，其余时间零维护。

## 5. 风险与坑

1. **次年数据真空期**：国务院公告每年 11 月左右发布，之前 date-holidays 对未来年份只能算"节日名"（无安排），UI 需容忍"暂无放假安排"状态，不要标错。
2. **date-holidays 的半天假噪声**：妇女节/青年节/儿童节/建军节（部分人群放假）在 CN 数据里 type 也是 public，UI 过滤策略要明确（建议默认只展示全体公民放假的节日，与中国法定口径对齐）。
3. **时区表述**：date-holidays 以 `Date` 对象交互（返回 UTC start/end），全链路应统一 Date ID 字符串（`"YYYY-MM-DD"`），与 FlashCalendar 契约一致，禁手工 `toISOString` 转换（同《日历公共组件规范》Date ID 数据契约）。
4. **包体积**：date-holidays 全量 10.97 MB 绝不能整包进 RN bundle；走构建期生成 JSON 路线（方案 A）。chinese-days 623 KB 可直接打包。
5. **精度预期**：伊斯兰地区假日依历法观测确定，规则引擎与任何数据源都可能偏差 1 天；文档口径写"以当地政府公告为准"。
6. **选型必须实测 require()**：chinese-workday 的打包缺陷在 README 与元数据里完全看不出来，跑一次才知道。
