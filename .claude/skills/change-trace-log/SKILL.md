# 全链路变更日志（docs/logs）

## 触发条件

一次任务产生实际代码改动并完成验证后，除 `CHANGELOG.md` 条目外，在 `docs/logs/` 写一篇日志。合并带入功能时同样适用（基点为 merge-base 提交）。豁免：纯文档、CHANGELOG 记录本身、无行为变化的格式化提交；有疑义时写。

## 文件命名

`docs/logs/YYYY-MM-DD-<英文短题>.md`，一天多篇加 `-2`、`-3` 序号。日期取当天实际日期。

## 编写流程（顺序执行，不得跳步）

1. **确定基点**：合并用 `git merge-base <本分支> <来源>`；追加修改用改前的工作区/HEAD。记录基点提交 SHA。
2. **实测对比**：用 `git diff <基点>..<结果> --stat` 和逐文件 `git diff` 取证。禁止只看最终代码臆测"原来"的行为。
3. **追踪链路**：从触发源（UI/订阅/闹钟/广播）到落点（Store/SQLite/原生/API）走一遍真实代码，确认每一跳的文件与函数名。
4. **落盘日志**：按下文模板写，与代码改动同一次提交入库。

## 日志模板

```markdown
# <功能或修复一句话标题>

- 日期：YYYY-MM-DD
- 基点：`<提交 SHA 或描述>` → 结果：`<提交 SHA 或工作区>`
- 关联：CHANGELOG 对应条目时间戳 / 相关分支或 PR

## 一、改动清单（按层）

按 `src/features → src/core → src/shared → modules/ → tests → docs` 分层；
新增文件写行数与职责，修改文件写具体改动点（含默认值/开关反转的单独标注）。

## 二、与原代码对比

逐点写「原来是什么 → 现在是什么」，标注行为反转项；
每点给出证据（diff 位置或原函数名）。

## 三、改动原因

每个实质改动写清"为什么改"：原方案的问题、触发的需求或缺陷、
设计取舍（权限独立性、防抖动、冷启动防护、并发安全等）。

## 四、完整调用链路

文字或 ASCII 链路，从触发源到落点，标注：
双端镜像逻辑（JS/Kotlin 等同语义的两份实现）、唯一入口、
门控与降级分支、失败与回滚路径。

## 五、验证情况

实际执行的命令与结果；未执行的明确写"未执行"。
```

## 质量红线

- 写实优先：不确定的链路去代码里确认，宁可不写，不得编造。
- 对比必须来自 diff 实测，引用真实提交号。
- "为什么"至少答到设计取舍层，不停留在"需求要求"。
- 日志只写与代码一致的现状；后续重构使旧日志过时时不必回改旧日志，但新日志需引用并说明差异。
